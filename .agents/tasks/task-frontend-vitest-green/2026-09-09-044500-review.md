# Harden undefined-array reads in provider/model-selector UI and align app.test IPC mock (v1)

The frontend vitest suite was the sole remaining red step on `feat/provider-visibility-diagnostics`; the just-added commit (`7d4a2a7`) is a scoped fix for it. The root cause was a missing `list_cloud_providers` case in `app.test.tsx`'s `routeInvoke`, so `invoke` resolved `undefined`, `ProviderKeysSection`'s mount effect set `providers = undefined`, and the render-time `providers.length > 0` threw, tearing down the Settings render and cascading into the "switches to History and Settings" test. The fix works on two fronts: it hardens every IPC-array assignment in `ProviderKeysSection`, `LocalRuntimesSection`, `ProviderEnumerationErrors`, and `ProviderModelPicker` with `Array.isArray(next) ? next : []` so a non-array resolve can never reach a `.length`/`.map`/`.filter`, and it adds the missing `routeInvoke` cases (`[]` for the three list commands, `{ loadedModelId: null, registeredCount: 0 }` for `embedded_model_status`).

Watch for: nothing blocking. The guards are real-app robustness, not test-only patches, and the mock shapes are faithful to the Rust command return types (confirmed) — the previously-throwing path now hits an always-array value, and no other unguarded IPC-array read remains in the reworked UI (confirmed).

**Verdict**: APPROVED

## High-level view

The failure was a mock gap, but the fix correctly treats both surfaces: the source-level `Array.isArray` normalization means the UI survives a malformed/absent IPC field at runtime, not just under the test mock, so it does not merely paint over the test. Every component the diff touches reads its array either from the newly-guarded local resolve or from the providers store, which initializes `models`/`errors` to `[]` and defaults them with `?? []` in `load()`; no remaining unguarded array read in the reworked model-selector or settings surfaces would trade this failure for the next (confirmed).

The added `routeInvoke` cases match the real command contracts: `list_cloud_providers`, `list_local_runtimes`, and `list_embedded_models` are all `Result<Vec<…>>` on the Rust side (arrays), and `embedded_model_status` returns the `{ loadedModelId, registeredCount }` shape (serde camelCase confirmed by the backend's own JSON assertion), matching the `EmbeddedModelStatus` TS type. The mock does not drift from the shapes production returns.

No feature behavior is regressed. The cloud-registration path (`set_cloud_provider` persisting a real `ProviderConfig`), the Ollama IPv4-loopback + `Accept: application/json` hardening, and the enumeration-error surfacing all live in earlier feature commits on the branch and are untouched by this commit; those changes plausibly address the user's two underlying reports (Kiro/Gemini keys doing nothing; Ollama models not appearing), and this commit neither masks nor weakens them. The edits introduce no unused bindings and no type changes, so eslint `no-unused-vars` and `tsc` have no new surface to fail on.

### The failing path and why the guard closes it

`ProviderKeysSection` renders `{providers.length > 0 && (…)}`, and on mount it did `listCloudProviders().then((next) => setProviders(next))`. Under the old `app.test` mock, `list_cloud_providers` fell through to `routeInvoke`'s `default: return undefined`, so `setProviders(undefined)` ran and the next render read `undefined.length` — a synchronous throw during Settings render that cascaded into the navigation test. The fix both guards the assignment (`Array.isArray(next) ? next : []`) and adds the `list_cloud_providers` mock case. Either alone turns the suite green; together the guard protects the real app against a backend returning a malformed or fieldless payload while the mock keeps the test exercising the true contract.

The same guard is applied everywhere a raw IPC resolve feeds a setter that later hits an array method: `LocalRuntimesSection`'s mount (`listLocalRuntimes`/`listEmbeddedModels`), `clearRuntime`, `importModel`, and `loadPath`; and the two presentational props (`ProviderEnumerationErrors.errors`, `ProviderModelPicker.models` in both the exported picker and the inner `ModelGroup`). `embeddedModelStatus`/`setStatus` is deliberately left unguarded — it flows into `status?.loadedModelId ?? null`, never an array method.

### No remaining unguarded array read trades one failure for the next

The two other consumers of provider data — `PerMessageOverrideControl` and `RoutingModeToggle` — read `models.length` (and `errors`) directly without an `Array.isArray` guard, but they source those values from the zustand providers store, not a raw IPC resolve. The store initializes `models: []` and `errors: []` and its `load()` sets `{ models: result.models ?? [], errors: result.errors ?? [] }`, so both are structurally always arrays. `app.test`'s `beforeEach` resets the store with `setState({ models: [] })` and does not re-set `errors`; because zustand merges, `errors` retains its always-array default, so the missing key is not a latent throw.

### Mock shapes match the real command contracts

Checked against `crates/tauri-app/src/commands.rs`: `list_local_runtimes` → `Result<Vec<LocalRuntimeConfigView>>`, `list_cloud_providers` → `Result<Vec<CloudProviderConfigView>>`, and `list_embedded_models` → `Vec<EmbeddedModelView>` all serialize as JSON arrays, so `[]` is a faithful empty stand-in. `embedded_model_status` returns `EmbeddedModelStatus`, whose serde output the backend's own test asserts as `{"loadedModelId":…,"registeredCount":…}`, matching the `{ loadedModelId: null, registeredCount: 0 }` mock and the TS `EmbeddedModelStatus` interface (`loadedModelId: string | null; registeredCount: number`).

### Underlying user reports are addressed by feature code, not masked by this fix

The user's two symptoms — adding Kiro/Gemini keys "does nothing," and a reachable Ollama's models not showing — are handled by earlier commits on the branch this fix does not touch. Cloud registration now persists a real `ProviderConfig` row via `set_cloud_provider` (addressable by a stable per-kind id and consumed by the enumerate path), replacing the old dead-end that only stored a secret plus a localStorage marker. Ollama discovery now defaults to the IPv4 loopback literal `127.0.0.1:11434` instead of the `localhost` hostname (avoiding the `::1`-first resolution that makes reqwest get connection-refused while `curl` silently retries the other family) and sends an explicit `Accept: application/json`, with a decode test over the exact rich `/api/tags` payload the user pasted. Critically, the `Array.isArray`/`?? []` normalization does not swallow a real enumeration error: errors surface through the separate `errors` channel (`ProviderEnumerationErrors`), which the model-selector tests now assert renders alongside a populated picker.

### Lint and type surface

The edits add only local `const items`/`const list` bindings that are immediately used, swap direct prop reads for those bindings, and add `case` labels plus one object literal in the test mock — no imports, exports, or type signatures changed, so there is no new `no-unused-vars` target and no `tsc` surface to break. This rests on reading the diff, not running the tools: the sandbox has no `node_modules` and the npm registry is blocked, so vitest/tsc/eslint could not be executed to confirm the green run empirically.
