# Self-reporting model-enumeration diagnostics for the empty picker (v1)

The built Windows app has shown "No models available yet" with no models and no error across four releases, and nothing on the load path self-reported what happened. This change makes the enumeration path visible from three angles: the shared `list_available_models` now records a configured row that never built an instance as a display-safe error instead of silently `continue`-ing; the Tauri picker path builds the registry per-row (resilient) instead of fail-fast so one un-buildable row can't abort the whole list; and a new display-safe `provider_diagnostics` command plus a Settings "Diagnostics" section and a chat status line give the user a copyable, per-provider readout of exactly what the picker saw. The frontend store's `load()` now captures an IPC rejection into `loadState`/`lastError` instead of swallowing it.

Watch for: (1) **confirmed** — `provider_diagnostics_inner` re-implements the per-row enumeration inline rather than calling the shared `providers::list_available_models`, so its "same reality" guarantee rests on two loops staying in sync (including a verbatim-duplicated error string); a future edit to one won't force the other. (2) **confirmed** — the `send_message` routing path (`commands.rs:1579`) still uses fail-fast `providers::build_registry(...)?`, so the resilience posture the picker now has is not shared by the send path; this is pre-existing/unchanged and out of scope, but it means an un-buildable row that the picker tolerates can still fail a send. (3) **confirmed** — display-safe discipline holds: nothing in the new command return, TS types, or UI surfaces `api_key_ref`, a resolved secret, or key material.

**Verdict**: APPROVED

## High-level view

The invisible-skip fix is the core behavioral change: `providers::list_available_models`'s `None` branch (no built instance for a configured row) now pushes a `ProviderEnumerationError` with a static, secret-free message instead of dropping the row. That single change is what turns "contributed nothing, said nothing" into a diagnosable per-provider error, and both the picker path and the new diagnostics command depend on it.

The picker path (`list_available_models_inner`) swaps fail-fast `build_registry(...)?` for a resilient loop: seed from `builtin_registry()`, `build_from_config` per row, ignore per-row build errors. Combined with the invisible-skip fix, an un-buildable row surfaces as a per-provider error rather than a thrown `CommandError` that blanks the whole list. This resilience is local to the picker path; the routing/send path was left on the old fail-fast call.

`provider_diagnostics` is a new display-safe command whose `_inner` reproduces the picker's seeding, resilient build, and shared-`EmbeddedProvider` insertion, then reports per-row `{ id, kind, baseUrl, instanceBuilt, modelCount, error }` plus summary counts. It mirrors the picker faithfully today, but by duplicating the enumeration loop instead of calling the shared function it takes on a drift risk.

The frontend closes the last silent-empty cause: `load()` wraps the IPC call so a rejection becomes `loadState:"failed"` + `lastError` instead of an unhandled promise from `void load()`. A copyable chat status line and an always-reachable Settings "Diagnostics" section render the outcome, both defensive against undefined arrays, nulls, and IPC throws.

The API surface is one new command (`provider_diagnostics`, registered in `generate_handler!`), one IPC wrapper, and two hand-mirrored TS types; no env vars or flags.

### Invisible-skip fix in the shared enumeration

The behavioral root cause was a `let Some(instance) = registry.get(&cfg.id) else { continue };` in `providers::list_available_models`: a configured row whose factory build failed or was skipped resolved to no instance, so it contributed neither a model nor an error and vanished from both the picker and the error list. The `None` branch now pushes a `ProviderEnumerationError { provider_id, message }` with a static string that names the failure class ("provider is configured but no instance was built … it cannot be enumerated") and carries no secret material. This is the load-bearing change; the picker resilience and the diagnostics command both rely on it to convert an un-buildable row into something the UI can display.

The regression test `a_config_row_without_a_built_instance_is_recorded_as_an_error` drives an empty `builtin_registry()` with one configured row and asserts exactly one error, empty models, the right `providerId`, a non-empty message, camelCase serialization, and absence of `apiKey`/`secret`. It would fail if the `continue` were restored, so it genuinely pins the fix rather than asserting static shape.

### Resilient per-row registry build in the picker path

`list_available_models_inner` previously called `providers::build_registry(configs.iter(), …)?`, which delegates to `build_all` and short-circuits on the first build failure via `?`. One un-buildable row therefore became a thrown `CommandError` that rejected the whole enumeration — a clean-empty cause with no visible error. It now seeds `providers::builtin_registry()` and calls `registry.build_from_config(cfg, …)` per row, discarding per-row build errors with `let _ =`. A failed row is left un-built, and the invisible-skip fix then surfaces it as a per-provider error. `providers::build_registry` is fully qualified at the old call sites, so removing it here introduces no unused import and no clippy `-D warnings` risk from this swap.

### provider_diagnostics: faithful mirror, duplicated by construction

`provider_diagnostics_inner` reproduces the picker's setup step for step: `ensure_ollama_provider_config` (and, as in the picker, *not* `ensure_embedded_provider_config`), `ProviderRepo::list`, `AppConfig::load` + `pricing_table_from_config` (loaded but unused, kept only to keep the sequence identical), the same `builtin_registry()` + per-row `build_from_config` loop, and the same `insert_instance(EmbeddedProvider::from_shared(state.embedded_engine.clone()))` shared-engine bridge.

```
list_available_models_inner            provider_diagnostics_inner
  ensure_ollama_provider_config          ensure_ollama_provider_config
  ProviderRepo::list                     ProviderRepo::list
  AppConfig::load + pricing (used)       AppConfig::load + pricing (unused, parity only)
  builtin_registry + build_from_config   builtin_registry + build_from_config   <- identical
  insert EmbeddedProvider::from_shared   insert EmbeddedProvider::from_shared    <- identical
  list_models(...)  (shared fn)          inline per-row get→list_models loop     <- DIVERGES
```

The divergence is the last row: the picker calls the shared `providers::list_available_models`, while diagnostics re-implements the get-instance/`list_models`/count-or-error logic inline and repeats the "no instance was built" message verbatim. Today the two agree — `model_count` counts `models.len()` and each model maps to exactly one `AvailableModel`, so counts match — but nothing forces them to stay agreed. If the shared function's per-row semantics change (e.g. dedup, filtering, a different skip rule), the diagnostics readout silently stops mirroring the picker, which is precisely the "misleading diagnostics" failure this task is trying to avoid. Consuming the shared enumeration result, or factoring the per-row step into one helper both call, would make the mirror structural instead of maintained-by-hand.

`provider_diagnostics_inner_reports_seeded_ollama_row` and `provider_diagnostics_inner_reports_unbuildable_row` exercise the real `_inner` against a test state: the first asserts the seeded `ollama-local` row builds (`instanceBuilt == true`) but errors on enumeration offline (`modelCount == 0`, non-empty error) with camelCase, secret-free serialization; the second persists a `GenericOpenAI` row with no `base_url` (its factory requires an endpoint), asserts `instanceBuilt == false` with a display-safe error, and that other rows survive. The second would fail if the build were fail-fast again, so per-provider isolation is genuinely pinned.

### Display-safe discipline across the new IPC boundary

`ProviderDiagnostic` carries `id`, `kind`, `base_url: Option<String>`, `instance_built`, `model_count`, and `error: Option<String>`; `ProviderDiagnosticsReport` adds three counts. `base_url` is the persisted display string (architecture.md treats it as display-safe), and `error` is only a `ProviderError` `Display` string. There is no `api_key_ref`, no resolved `SecretRef`, no key material anywhere in the return type, the TS mirror, or the `DiagnosticsSection` render (which prints id/kind/baseUrl-or-"default"/instanceBuilt/modelCount/error). The build loop resolves keys through the secret store to *build instances*, but nothing from that resolution reaches the report. Both backend tests assert the serialized JSON contains no `apikey`/`secretref`, so the invariant is checked, not just claimed.

### Frontend load() no longer swallows an IPC rejection

The store's `load()` set `models`/`errors` from a bare `await listAvailableModels()`. Since `app.tsx` fires the startup load as `void …load()`, a rejected IPC call left `models:[]`/`errors:[]` with no signal — clean-empty cause A. It now sets `loadState:"loading"`, and on rejection sets `loadState:"failed"` + `lastError` while leaving prior `models` intact (a transient refetch failure won't wipe a good list). The consequence worth noting: on a *first* failed load `models` is still `[]`, so any "is the picker empty?" decision must consult `loadState`/`lastError`, not `models.length`. The added consumers do. `load captures an IPC rejection …` asserts the promise resolves (does not throw) and records `failed` + the message, which would fail if the try/catch were removed.

### Chat status line and Diagnostics section: defensive rendering

`PerMessageOverrideControl` renders a copyable `data-testid="model-load-status"` line reading `loading…`, `loaded N models from M providers`, or `failed: <error>`, guarding `models` with `Array.isArray` and deriving provider count from a `Set` over `providerId` (a field that exists on `AvailableModel`, so the map is type-safe). `DiagnosticsSection` runs `provider_diagnostics` on mount, tracks `loading`/`error`/`report`, guards every read of the possibly-null `report` behind those states, guards `report.providers` with `Array.isArray`, and renders `failed: <error>` on an IPC throw so the panel is never blank. The `useEffect(() => { run(); }, [])` mount pattern will trip `react-hooks/exhaustive-deps`, but lint runs without `--max-warnings 0`, so it is non-fatal. The Diagnostics section is wired into the `SettingsSection` union, `SECTIONS`, and the render switch as an always-reachable section — which matters because it must be usable precisely when the picker is empty.

### Test coverage and what runs where

Frontend tests cover the store success/failure transitions, the chat status line's loaded and failed text, the `providerDiagnostics()` wrapper invocation, and the Settings section's summary/list/refresh plus the IPC-throw path; every `<App/>`/`<Settings/>`/model-selector suite gained a `provider_diagnostics`-safe mock so the new mount-time IPC call never resolves `undefined`. Backend tests cover the invisible-skip regression and both `provider_diagnostics_inner` scenarios. Not tested: the structural agreement between `provider_diagnostics_inner`'s inline loop and the shared `list_available_models` (nothing would catch a future drift between them), and the `send_message` resilience asymmetry (no test asserts whether an un-buildable row aborts a send). Per the environment, `cargo test`, `vitest`, `clippy`, `eslint`, and `tsc` run only in CI; only `cargo fmt --check` (both crates) and prettier run offline here, and both pass.
