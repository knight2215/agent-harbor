# Making "Auto" routing real: chat-only candidate pool, per-model capabilities, seeded pricing, and a quality tier

This branch fixes the three root causes behind "Auto doesn't actually route": the Gemini picker listed ~48 models (embeddings, TTS, image, video, transcription) all stamped `streaming · tools · vision · json · free`, every model scored identically so Auto couldn't differentiate, and a retired id like `gemini-2.5-pro` failed mid-turn with a 404. The fix filters enumeration to `generateContent`-capable models using Gemini's `supportedGenerationMethods`, grounds each model's `Capabilities` in its real metadata (`inputTokenLimit`, per-family vision), seeds the pricing table from `bundled_defaults()` so cloud models are no longer "free", and adds a per-model `quality` tier that `AutoDefaultPolicy` blends into its complexity ranking. The 404 path was confirmed already-correct (error surfaces verbatim) and pinned with a test; enumeration-time deprecation filtering and an Auto fallback-hop were deliberately deferred.

**Watch for:** (1) the frontend picker fixture hand-sets `vision: false` for `gemini-2.5-flash-lite`, but the real backend `is_multimodal_family` returns `vision: true` for that id — the two test suites disagree about the same model (confirmed); (2) the quality blend changes absolute scores for all existing routing fixtures (now `0.5*caps_proxy + 0.25`), and routing can't be compiled/tested in-sandbox, so thin-margin existing ranking tests are unverified (possible); (3) `quality_for` matches `8b` as a bare substring (confirmed, low impact).

**Verdict**: APPROVED

## High-level view

The candidate-pool filter is the load-bearing change. `list_models` switched from `map` to `filter_map`: the primary signal is Gemini's per-entry `supportedGenerationMethods` (keep only `generateContent`/`streamGenerateContent`), and a name-family backstop (`is_non_chat_model_name`) only fires when that list is absent. The backstop is deliberately fail-open — an unrecognized name is kept — so a new chat model is never silently dropped. This is the right asymmetry for a picker.

Per-model capabilities now flow through a new internal-only `ModelInfo.capabilities: Option<Capabilities>` that does not cross IPC; enumeration prefers it over the coarse string-based `capabilities()` stamp. Vision is claimed only for the documented multimodal families via `is_multimodal_family`, and `max_context` comes from `inputTokenLimit`. Note that `is_multimodal_family` treats every `gemini-2*` flash/pro as multimodal, including `flash-lite` — that's a backend decision the frontend fixture contradicts.

Cost is fixed at the seam where it broke: `pricing_table_from_config` now starts from `PricingTable::bundled_defaults()` and overlays user rates, instead of starting empty. This is a one-line root-cause fix with a direct regression test.

The `quality` tier is a new `f64` on the IPC DTO `AvailableModel`, resolved by a generic per-family/per-kind `quality_for` map and blended equal-weight with the caps/context proxy in `quality_for_complexity`. The blend preserves ordering when quality is equal but compresses the caps/context spread; every construction site across five crates plus the TS mirror was updated.

The 404 resilience is a no-op in production code — the path already surfaced the provider error verbatim — so the change is purely a pinning test. The two things a reviewer might expect but won't find (enumeration-time deprecation filtering, an Auto fallback-to-next-candidate hop) were consciously deferred with rationale.

### Chat-capable candidate pool via `supportedGenerationMethods`

The picker pollution had a single cause: `list_models` mapped every `/v1beta/models` entry into a `ModelInfo` with no capability filter. The fix reads three previously-ignored fields (`supportedGenerationMethods`, `inputTokenLimit`, `outputTokenLimit`, all `#[serde(default)]`) and switches the pipeline to `filter_map`. A model survives only if its methods list contains `generateContent` or `streamGenerateContent`; when the methods list is present but lacks both, the model is dropped outright. That reliably removes `embedContent` (embeddings), `predict` (image/video), TTS/`countTokens`, and the rest of the non-chat families the user saw.

The interesting design decision is the backstop. `is_non_chat_model_name` runs **only** when the methods list is empty, and it is fail-open: it drops a fixed set of obvious non-chat families (`embedding`, `-tts`, `native-audio`, `-transcribe`, `-image`, `imagen`, `nano-banana`, `veo-`, `lyria-`, `robotics`, `computer-use`, `aqa`, `deep-research`, `antigravity`) and keeps anything it doesn't recognize. This is the correct direction to fail for a model picker — a false negative shows one junk model, a false positive hides a real one. The unit test `non_chat_name_backstop_matches_known_families_only` pins both directions, and two wiremock tests cover the methods-present and methods-absent paths.

One sharp edge lives in the backstop substring set. `aqa` is three characters and `-image` is a common token; either could match a future chat id if Gemini ever ships one whose entry also omits the methods list. Both conditions are unlikely together, and the primary signal shadows the backstop whenever the API populates the methods list, so this is a low-severity note rather than a blocker.

### Per-model capabilities through an internal `ModelInfo.capabilities`

Capabilities previously came from `instance.capabilities(&model.id)`, a per-string lookup that couldn't see the listing metadata, which is why every Gemini row read the same. The chosen path enriches `ModelInfo` with `capabilities: Option<Capabilities>` and has enumeration prefer it:

```rust
let capabilities = model
    .capabilities
    .unwrap_or_else(|| instance.capabilities(&model.id));
```

The `Option` is internal-only and does not cross IPC (only `AvailableModel` does), so no frontend mirror change was needed — verified against the diff, which touches no `ModelInfo` TS type. `caps_from_metadata` sets `max_context` from `inputTokenLimit` and `caps_for` delegates to it with `None`, so the metadata-less path applies the same per-family vision truth without drifting.

The vision rule is where backend and frontend disagree. `is_multimodal_family` matches `(gemini-1.5 | gemini-2 | gemini-3) && (pro | flash)`, so `gemini-2.5-flash-lite` — which contains `gemini-2` and `flash` — reads as **vision-capable**, and the adapter test asserts exactly that (`assert!(lite_caps.vision, "gemini-2.5-flash is multimodal")`). But the new frontend picker fixture builds `gemini-2.5-flash-lite` with `vision: false` to demonstrate "different capability labels". The frontend test is asserting a capability shape the backend would never emit for that id. Since the fixture is hand-authored rather than derived from backend output, nothing catches the drift — the vitest test passes on fabricated data while the Rust test passes on the real rule. Decide whether flash-lite should claim vision, then make both suites agree.

### Pricing seeded from bundled defaults

The "everything free" bug was a single wrong starting point: `pricing_table_from_config` began from `PricingTable::new()` (empty), so with no user rates every `price_for` returned zero and the picker's zero-price heuristic filed paid cloud models as local/free. The fix starts from `PricingTable::bundled_defaults()` (nonzero cloud rates, Gemini ~1.25/5.0; zero for genuinely-local kinds) and overlays the persisted per-kind/per-model rates so user overrides still win. `pricing_table_seeds_bundled_defaults_so_cloud_is_not_free` asserts a Gemini row is nonzero and Ollama/LM Studio stay `ZERO` under an empty config — a direct regression test for the reported symptom.

### The quality tier and its blend into ranking

`AvailableModel` gains `quality: f64` (`#[serde(default)]`, camelCase key `quality`), resolved by `quality_for(kind, id)` from a family map: lean 0.4 (`flash-lite`/`mini`/`nano`/`haiku`/`-small`/`8b`, checked first), top 0.9 (`pro`/`opus`/`ultra`/`4o`/`gpt-4`), mid 0.6 (`flash`/`sonnet`/`turbo`/`medium`), local kinds 0.5, else `DEFAULT_QUALITY` 0.5. The ordering is deliberate and correct: `gpt-4o-mini` hits the lean rule before `4o`/`gpt-4`, so it lands at 0.4 not 0.9. The one rough edge is `id.contains("8b")` as a bare substring — it exists to catch `qwen3:8b` but would also catch any id with "8b" embedded. It's an overridable default, so impact is low, but anchoring it would remove the surprise.

The blend is the behavioral core:

```rust
let caps_proxy = (cap_score + ctx_score).min(1.0);
let tier = model.quality.clamp(0.0, 1.0);
let base = (0.5 * caps_proxy + 0.5 * tier).min(1.0);
```

Blending rather than replacing keeps the caps/context signal that already separated a small-context tool-less model from a large-context one, while letting the explicit tier break ties between otherwise-identical models (the ~48 Gemini rows). The four new tests exercise the intended behaviors: high complexity prefers higher quality at equal caps/price, PreferQuality picks the stronger model, PreferLocal stays local, and low complexity still prefers the cheaper adequate model.

The unverified risk is the effect on **existing** fixtures. Every prior routing fixture now carries `quality: 0.5` (via the `model` helper delegating to `model_q(..., 0.5)`), so their `base` changed from `caps_proxy` to `0.5*caps_proxy + 0.25`. Ordering is preserved whenever two candidates share the same quality (the comparison stays monotonic in `caps_proxy`), which is the common case, so the existing tests should hold. But the spread between candidates is compressed, and the final decision also folds in a cost weight — a pre-existing test whose expected winner was decided by a thin caps/context margin could flip once that margin is halved. Because the routing crate cannot be compiled or tested in this sandbox (rustc 1.92 vs AWS-SDK transitive deps), this is exactly the class of regression a hand-audit can miss. The CI `cargo test -p routing` run is the gate; confirm the pre-existing auto_default and signals ranking assertions still pass, not just the four new ones.

### 404 handling: a pinning test over an already-correct path

There is no production change here — `orchestrator-core/src/` is untouched in the diff. The provider `HttpStatus { status, body }` error already maps through `PipelineError::Provider` (Display `provider error: {0}`), and `run_turn` already emits `CoreEvent::MessageError` and persists an Error-status message carrying that string, so Google's replacement suggestion surfaces verbatim. The new `provider_404_propagates_verbatim_to_message_error` test adds an `ErroringProvider` and asserts all three surfaces (the returned `PipelineError`, the emitted `MessageError`, and the persisted message content) contain `404` and `gemini-3.1-pro-preview`, locking in the behavior the user complained about.

Two deferrals are documented and reasonable. Enumeration-time deprecation filtering was skipped because Gemini's listing exposes no reliable deprecation marker — filtering on a guessed `description` substring would risk dropping live models, so relying on ranking-toward-current plus the verbatim error is the safer call. The Auto fallback-to-next-candidate hop was deferred because `run_turn` is a single routing decision followed by a bounded tool loop; a clean one-hop retry would require reworking that flow, which is beyond an input-enrichment change. Both are the right scope calls for this branch; they're listed as issues only so the follow-up is tracked.

### Construction-site and clippy audit (compile-critical, CI-gated)

The compile-critical question — does every `AvailableModel` literal set the new `quality` field — checks out. The sole production builder (`list_available_models_with_build_errors`) sets `quality = quality_for(cfg.kind, &model.id)`; the test/literal sites in `signals.rs`, `manual_override.rs`, `registry.rs`, `demo_policy_extension.rs`, `auto_default.rs` (via `model_q`), `pipeline_e2e.rs` (both), and `commands.rs` (both) all add `quality`. The provider tests (`demo_provider_extension.rs`, `net_peer.rs`) build through the real enumerator, not literals, so they're unaffected — confirmed by grep. `output_token_limit` is read (`context_length: m.input_token_limit.or(m.output_token_limit)`) so it isn't dead code, and `caps_for` remains reachable via `capabilities()`. The remaining clippy-class risks (needless_lifetimes, unused imports) can't be machine-checked here since clippy is CI-only; the hand-audit found none, but treat CI clippy as the authority.

### Test coverage

Covered: methods-list filtering (keep chat, drop embeddings/TTS), the name-family backstop in both directions, differentiated per-model caps/context, the pricing seed fix, the quality tier map, four quality-blend ranking scenarios, the 404 verbatim propagation across all three surfaces, and a frontend picker test rendering per-model caps and cloud-vs-local grouping.

Not tested: the interaction between the compressed quality blend and the pre-existing routing fixtures (the regression risk above — no in-sandbox run); the frontend picker's `flash-lite` vision claim against real backend output (the fixture fabricates `vision: false`, which the backend contradicts); and any end-to-end assertion that a real Gemini `/v1beta/models` response shape (as opposed to the wiremock fixtures) decodes correctly.
