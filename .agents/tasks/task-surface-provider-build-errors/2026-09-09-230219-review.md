# Surface the real per-row provider build error in the picker and diagnostics

The v0.7.3 diagnostics readout collapsed every configured-but-unbuilt provider to one useless line — "provider is configured but no instance was built ... it cannot be enumerated" — because both `list_available_models_inner` and `provider_diagnostics_inner` threw away the `Err(ProviderError)` from `registry.build_from_config` via `let _ =`. This change captures each per-row build failure into a `BTreeMap<String,String>` keyed by `cfg.id` and threads it through a new shared seam `providers::list_available_models_with_build_errors`, which prefers the real error over the generic fallback for an unbuilt row. A second, independent piece adds non-blocking advisory guidance (backend + frontend) that steers users away from pasting a Kiro session URL or a Gemini `:generateContent` endpoint into the generic-OpenAI base-url field. The third commit is docs-only.

Watch for: a frontend/backend advisory asymmetry — the TS advisory also flags the bare `generativelanguage.googleapis.com` host, but the Rust advisory does not (confirmed); the shared build-error seam is display-safe by construction and the v0.7.3 non-fatal behavior is preserved (confirmed).

**Verdict**: APPROVED

## High-level view

The fix is a clean widening of the enumeration API: the 3-arg `list_available_models` now delegates to a 4-arg `list_available_models_with_build_errors` with an empty map, so external callers keep their signature and their generic-fallback behavior, while the two tauri-app callers pass the errors they used to discard. Diagnostics stays derived from the same shared enumeration, so the picker and the Diagnostics panel cannot drift — the exact drift risk that motivated deriving diagnostics in the first place.

Display-safety rides on one property: `build_errors` values are `ProviderError` `Display` strings, which name a failure class and reason (a missing handle, a bad base_url) but never resolved key material. A new contract test pins that the `Auth` variant's Display carries the reason and no `sk-`/`AIza` token, and the diagnostics tests assert no `apikey`/`secretref`/key literal crosses the serialized boundary.

The advisory guidance is deliberately non-blocking and narrow: link-local/metadata IPs remain the only case that rejects a save. The backend flags only `/session/` and `:generateContent` shapes; the frontend flags those plus the `generativelanguage.googleapis.com` host. That host gap is the one behavioral inconsistency worth a look, though the user's actual line-3 URL ends in `:generateContent` so both layers catch it.

The serde boundary is untouched — both view types already carried an `Option<String> warning` field, so the advisory rides the existing field and `types/index.ts` needed no edit. That invariant is verified, not assumed.

### The `build_errors` seam and backwards-compatible delegation

The public 3-arg `list_available_models` becomes a one-line delegation to `list_available_models_with_build_errors(..., &BTreeMap::new())`. Only the unbuilt-row branch changed: `build_errors.get(&cfg.id).cloned().unwrap_or_else(|| generic)`. Every other path — the `Some(instance)` enumeration, the model attribution, the pricing join — is byte-identical, so the existing `demo_provider_extension.rs` external test and any other caller keep the generic-fallback behavior with no code change, and the fix is confined to callers that captured a cause. `BTreeMap` is already imported at builtins.rs:24, so no new import.

The two tauri-app callers now do `if let Err(err) = registry.build_from_config(...) { build_errors.insert(cfg.id.clone(), err.to_string()); }` in place of `let _ = ...`. Per-row isolation is unchanged: a failing row is still left un-built, the other rows still build, and the loop never aborts — the only new effect is that the failure reason is retained instead of dropped. The auto-seeded `ollama-local` row builds successfully and takes the `Some(instance)` branch, so it is untouched by this change and still surfaces its one model.

### Diagnostics stays derived, not re-implemented

`provider_diagnostics_inner` continues to consume the shared enumeration result rather than running its own get/list/count loop, and now feeds it the same captured `build_errors` map. A row's `error` in the Diagnostics panel is, by construction, whatever the picker's enumeration recorded for that `provider_id`. Re-implementing the branch here would have reintroduced the drift risk the previous refactor removed.

### Display-safety of the threaded error

The whole fix hinges on `err.to_string()` being safe to surface. The values fed into `ProviderEnumerationError::message` are `ProviderError` Display strings. The new `contract.rs` test pins the risky variant directly:

```rust
let err = ProviderError::Auth("no secret found for handle 'gemini-cloud'".to_string());
assert_eq!(err.to_string(), "auth error: no secret found for handle 'gemini-cloud'");
assert!(!display.contains("sk-"));
assert!(!display.contains("AIza"));
```

The handle name (`gemini-cloud`) is a config id, not a secret. The two new diagnostics tests serialize the whole report and assert it contains no `apikey`, no `secretref`, and (in the keyed case) not the literal `AIza-test-key-do-not-leak` that was stored. `SecretStore::resolve` is the only plaintext path and it does not feed these Display strings.

### Test meaningfulness

The tests are behavioral, not tautological, and would fail on a revert. `build_errors_are_preferred_over_the_generic_message` asserts the recorded message is *exactly* the supplied real error and explicitly `!contains("no instance was built")`, then checks the empty-map delegation still yields the generic string — reverting `let _ =` would break the first half. The strengthened `provider_diagnostics_inner_reports_unbuildable_row` now asserts `err.contains("base_url")` and `!contains("no instance was built")`, so restoring the discard would fail it. `provider_diagnostics_inner_surfaces_gemini_auth_failure` persists a Gemini row whose key handle has no stored secret and asserts `instance_built == false` with the real "no secret found" reason — the user's actual line-1 failure. `provider_diagnostics_inner_builds_keyed_gemini_row` stores a key under `gemini-cloud` and asserts `instance_built == true`, pinning the traced by-key wiring (same handle stored and resolved). `advise_generic_openai_base_url_flags_only_non_api_shapes` asserts `https://host/v1`, `http://localhost:1234/v1`, and `https://kiro.example.com/v1` are all `None`, guarding against false positives on legitimate roots.

Not tested: the merge path where a plaintext-TLS warning AND a shape advisory are both present is exercised only indirectly (`merge_warnings` has no direct unit test). The Gemini `list_models` offline behavior is asserted only as `model_count == 0`, not on the specific enumeration error.

### Advisory guidance: non-blocking, and the host asymmetry

The backend `advise_generic_openai_base_url` strips query/fragment then flags `/session/` (contains) or `:generateContent` (ends_with), returning an advisory merged via `merge_warnings` into the single `warning` field — only for `ProviderKind::GenericOpenAI`, in both `set_cloud_provider_inner` and `set_local_runtime_inner`. It never blocks: the two backend tests assert the session/generateContent rows are persisted (found in `ProviderRepo::list()`) with a warning, and that `https://host/v1` / `http://localhost:1234/v1` carry no advisory. The blocking rule (link-local/metadata IPs via `validate_base_url`) is untouched.

The TS helper adds a third trigger the Rust helper lacks —

```ts
const isGeminiHost = host === "generativelanguage.googleapis.com";
if (looksLikeSession || looksLikeGenerate || isGeminiHost) { ... }
```

So a user pasting `https://generativelanguage.googleapis.com/v1beta/models` (a Gemini host root without `:generateContent`) gets a live client advisory, saves, and the persisted backend `warning` is silent — the two layers disagree on that URL. Not a correctness bug (the backend enumeration will still fail the row at build/enumerate time), but the asymmetry is a maintenance smell. The user's real line-3 URL ends in `:generateContent`, which both layers catch.

### Frontend advisory is duplicated

`adviseGenericOpenAiBaseUrl` is defined twice — identical logic in `ProviderKeysSection.tsx` and `LocalRuntimesSection.tsx`, differing only in the returned string's trailing "use the Gemini kind" hint. Both render a `role="status"` (non-blocking, distinct from the blocking error region) advisory plus a static inline `settings__field-help`. The vitest cases assert the advisory appears live before save, that save still fires `invoke` with the well-formed args, and that the backend `warning` surfaces afterward. Mount hygiene holds: the cloud test renders `<Settings />` whose default section is `providers`, so only `ProviderKeysSection` mounts and its `list_cloud_providers` + `list_available_models` calls are mocked with well-formed shapes; the local test mounts `LocalRuntimesSection` directly with all three local commands (`list_local_runtimes`, `list_embedded_models`, `embedded_model_status`) mocked correctly. Extracting the shared helper into one module would remove the drift risk.

### Serde boundary unchanged

`git diff` shows `frontend/src/types/index.ts` has zero changes, and both the cloud and local view structs already carried `pub warning: Option<String>` (commands.rs) mapping to `warning: string | null` (types/index.ts:225,244). The advisory reuses that field, so no boundary shape changed — invariant #4 verified directly.
