# Chat surface behaves like a chat, and a send can no longer fail silently (v1)

This branch fixes the reported "said hello to the local qwen3 Ollama model, got no reply and no error" bug and makes the composer feel like a real chat. The root cause was in the Rust `send_message_inner`: it built the provider registry with the fail-fast `providers::build_registry`, which short-circuits on the first un-buildable config row, so one misconfigured provider row rejected the entire send — and the frontend swallowed that rejection, producing a no-op with no message and no error. The fix builds the registry resiliently per-row (matching the sibling `list_available_models_inner`), so a single bad row is isolated and a working provider still routes. On top of that, the frontend now surfaces every send-path failure (a rejected `send_message` drives a `role="alert"` affordance; `messageError` carries the real reason into the bubble), the composer sends on Enter / newlines on Shift+Enter with an IME guard, and the message list renders as a threaded, role-styled conversation.

Watch for: (1) `send_message_inner` discards per-row build errors with `let _ =` while the sibling captures them — the send path shows *that* it failed but the specific build reason for the routing-relevant provider is only visible via the model picker (possible diagnostics gap, not a silent no-op). (2) On `status: "error"`, `MessageBubble` renders only text and hides any non-text content, so a tool-call/attachment bubble that errors shows the generic string (likely, minor). Neither blocks the fix.

**Verdict**: APPROVED

## High-level view

The backend change is a one-for-one port of the resilient per-row build already proven in `list_available_models_inner`. It isolates a misconfigured row instead of aborting the turn. The turn-failure contract is unchanged — `run_turn` still emits `MessageError` and persists an error message on any failure, including routing with no candidates — so a resilient build that yields an empty candidate set is still a visible error, not a new silent path.

Visibility is now guaranteed on both channels a send can fail through. A rejection *before* the turn spawns (registry/enumeration error, IPC failure) no longer escapes into a `void`-ed promise: the store captures it into `sendState:"failed"`/`sendError` and the composer renders "Failed to send: {reason}". A failure *during* the turn arrives as `messageError`, whose reducer writes the display-safe reason into the bubble and appends a fresh error bubble when no placeholder was ever seeded.

The `messageError` substitution is guarded so it can only overwrite an empty streaming placeholder (`{type:"text", text:""}`, exactly what `placeholderMessage` seeds); a reply that streamed real text and then errored keeps its text and only flips status. That asymmetry is deliberate and correct.

The composer adds Enter-to-send / Shift+Enter-newline with an IME-composition guard. `MessageList` becomes a scrollable role-styled thread with a token-only stylesheet and a jsdom-guarded auto-scroll anchor; both effects run before the early returns, so rules-of-hooks holds. No data-model or CoreEvent change.

Tests would each fail if the corresponding code were reverted (the Rust test rejects under the old fail-fast build; the store tests pin the empty-vs-streamed substitution branches; the composer tests separate Enter from Shift+Enter/IME). All store reset blocks across the three test files were updated with the new fields.

### Resilient per-row registry build in `send_message_inner`

The replaced block drops the fail-fast `providers::build_registry(configs.iter(), ...)?` for the same loop `list_available_models_inner` uses: `builtin_registry()`, then `build_from_config` per row, then the shared-embedded bridge via `EmbeddedProvider::from_shared(state.embedded_engine.clone())`. Send routing now observes the same providers the picker enumerates, which is the property that makes the reported symptom (a bad cloud/embedded row killing a working Ollama send) impossible.

The one intentional divergence from the sibling: this path uses `let _ = registry.build_from_config(...)` and does not collect `build_errors`, whereas `list_available_models_inner` captures them into a `BTreeMap` and threads them into `list_models_with_build_errors` so the picker shows the real cause. That produces an asymmetry: if the provider that *would* route is itself the un-buildable row, the send doesn't fail here (the row is simply absent), `list_models` returns an empty/partial candidate set, and the turn spawns. `run_turn` then raises a routing error and emits `MessageError`, so the user sees *a* failure — but the message is a generic "no route" rather than the specific build reason (missing secret, bad base_url), which is only discoverable by opening the model picker. Not a silent no-op, but a diagnostics gap worth a follow-up.

`list_models(&registry, &configs, &pricing).await?` still propagates enumeration errors as a rejected command. Pre-fix that rejection was swallowed; post-FEAT-002 it lands in `sendState`/`sendError`, so this residual reject path is now visible rather than silent.

### The turn-failure contract is intact

The fix leans on `run_turn` already emitting `MessageError` and persisting an `Error`-status message on any failure; routing with no candidates is a `RoutingError` caught by that same arm. So "resilient build yields zero candidates" is a visible error, not a new hole. `pipeline.rs` is unchanged on this branch; this is confirmation of the premise, not a reviewed change.

### Every send-path failure is now visible

Two distinct failure channels, both covered. A rejection before the turn spawns (registry build via `list_models?`, IPC transport failure, validation) previously escaped into the composer's `void sendMessage(...)` and vanished. Now `sendMessage` sets `sendState:"sending"`, awaits inside try/catch, resets to `idle` on success, and on reject sets `sendState:"failed"` with a display-safe `sendError` (`e instanceof Error ? e.message : String(e)`, mirroring `providers.ts` `load()`). The composer renders the `role="alert"` "Failed to send: {sendError}" only while `sendState==="failed"` — the only visible signal for a rejected `send_message`, which emits no CoreEvents, so it is load-bearing for the no-silent-no-op guarantee.

One caveat: `sendState`/`sendError` are store-global, not per-conversation, and are cleared only on the next send attempt. Switching to another conversation after a failed send leaves the stale alert visible against the new conversation until the user sends again.

### `messageError` reason substitution

The reducer branches three ways: an unknown `messageId` (failure before `messageStarted`) appends a new `status:"error"` assistant message with `content` text = `event.message`; an empty text placeholder gets the reason substituted; a message with non-empty text (streamed then errored on finalize) keeps its text and only flips status. The empty-check is `content.type === "text" && content.text.length === 0`, and `placeholderMessage` seeds exactly `{type:"text", text:""}`, so the guard aligns with what the store seeds and cannot overwrite a streamed reply.

The edge this leaves: a seeded placeholder whose content is *non-text* would fail the empty-check, keep its content, and drop `event.message`. Not something the current code produces for assistant turns, but not type-forbidden — worth a glance.

### Error rendering in `MessageBubble`

The error branch renders *either* the error paragraph *or* `ContentBody`, not both. This avoids double-rendering the text, but a non-text errored message (tool call, attachment) shows the generic "This message failed to generate." and hides its actual content — a display regression against the prior always-render-`ContentBody` behavior. Correct for the reported text-reply bug; flagged for the tool/attachment error states.

### Threaded view and rules-of-hooks

`MessageList` gains a `useRef` scroll anchor and a second `useEffect` keyed on `items.length` and `lastTextLength(items)` that calls `endRef.current?.scrollIntoView?.({block:"end"})`; the optional-call chain is the jsdom guard (jsdom has no `scrollIntoView`). Both effects were moved above the `activeConversationId === null` early return, so all hooks run unconditionally — rules-of-hooks safe. The stylesheet is token-only (`var(--ah-*)`).

### Test coverage

The Rust `send_message_inner_tolerates_unbuildable_provider_row` seeds a valid conversation plus an un-buildable GenericOpenAI row (no base_url) and asserts the command returns `Ok`. It mirrors the established `provider_diagnostics_inner_reports_unbuildable_row` setup and would fail against the old fail-fast `build_registry` — a genuine regression guard.

Frontend store tests pin all three `messageError` branches and both `sendMessage` outcomes. Component tests separate plain Enter (invokes `send_message`, clears draft) from Shift+Enter and IME (no invoke, draft preserved), assert the rejected-send alert plus store state, and assert stored-reason-vs-generic rendering. `beforeEach` does `invoke.mockReset()` then `mockResolvedValue(undefined)`; the mounted `MessageList` tests override `get_messages` with a well-formed array, so no chat component reads a shape off an undefined IPC result. All three test files had their store reset blocks updated with `sendState`/`sendError`, so nothing reads `undefined`.

Not tested (environment-bound): the live end-to-end silent-no-op cannot be reproduced (no live Ollama, no crates.io/npm in the sandbox), so `cargo`/`vitest` were not run here; verification is deferred to CI / the user's build. `cargo fmt --check` and `prettier --check` ran and passed offline.

### Clippy-level read

No unused imports introduced — `ProviderRepo`, `ProviderConfig`, `ProviderKind` are already imported and used; `providers::build_registry` was always fully-qualified and is now only referenced in comments, so no `use` became dead. `state.embedded_engine.clone()` is an `Arc` clone (not a needless deep clone). `let _ = registry.build_from_config(...)` is clippy-clean since the `Result` is not `#[must_use]`.
