# Populate the model picker at startup and refresh it on provider-config changes (v1)

The chat model picker showed "No models available yet" even after the user saved a working Kiro/Gemini key or had a reachable Ollama, because two wiring gaps left the picker's store empty and never refreshed. Bug A: the providers store's `load()` was only ever called from Settings > Providers & Keys, never at app startup or on chat-picker mount, so the singleton store began empty and stayed empty on the chat surface. Bug B: no backend command emitted `CoreEvent::ProvidersChanged`, so saving a key or starting a runtime never triggered a refetch. The fix loads the providers store once in the shell's single root effect, emits `ProvidersChanged` (fire-and-forget) after each successful provider-config mutation, drops the now-obsolete `#[allow(dead_code)]` on the event variant, and adds an always-available "Refresh models" button next to the chat picker so the already-placed enumeration errors finally surface there.

Watch for: the eight backend emit sites are covered by tests that replicate the wrapper's `_inner + emit` sequence rather than driving the `#[tauri::command]` wrapper, so the tests would still pass even if an emit call were dropped from a wrapper (**confirmed** — a real gap in regression protection for bug B). The startup `load()` is genuinely guarded by a dedicated app.test.tsx assertion and would fail if reverted (**confirmed**). No secrets are rendered by the new diagnostics (**confirmed**).

**Verdict**: APPROVED

## High-level view

Bug A is fixed in the shell's single root `useEffect`: it now calls `void useProvidersStore.getState().load()` once before opening the `onCoreEvent` subscription. The single-subscription invariant (opened once, torn down once, empty deps, fan-out to each store's `applyCoreEvent`) is preserved, and this is the correct place for a cache not owned by any one surface's mount.

Bug B is fixed by a private `emit_providers_changed(&AppState)` helper that sends `CoreEvent::ProvidersChanged` fire-and-forget through the existing `core_events` sender, mirroring the established `McpStateChanged` pattern. It is called in the thin command wrappers only after `_inner` returns `Ok`, so a rejected mutation emits nothing. All eight mutations named in the task (set/clear cloud, set/clear local runtime, embedded import/select/load/unload) are wired, and the `#[allow(dead_code)]` on the variant is dropped.

The diagnostics surface is minimal and display-safe: `ProviderEnumerationErrors` was already placed in `PerMessageOverrideControl`, and once startup `load()` runs in the chat context its `errors` populate and render as "Couldn't load models from <providerId>: <reason>". A new `aria-label`led "Refresh models" button calls the same `load()` for on-demand re-enumeration.

The regression protection is asymmetric. The frontend startup-load and refresh-affordance tests fail if the fix is reverted. The backend tests assert the emit helper works and that `_inner` errors short-circuit, but because they never invoke the actual `#[tauri::command]` wrappers, they do not protect against someone removing the `emit_providers_changed` call from a wrapper. The user's live build remains the only end-to-end proof, which the visible errors and refresh button are designed to make diagnosable.

### Startup hydration in the single root effect (bug A)

The load is placed inside the existing empty-deps root effect, immediately before `onCoreEvent` is opened, as `void useProvidersStore.getState().load()` — no new effect, no added deps, cleanup still tears down exactly one `UnlistenFn`. Because `DefaultRoutePicker`, `RoutingModeToggle`, and `PerMessageOverrideControl` all read the same singleton store, a single startup load populates every chat-side picker at once.

The app.test.tsx coverage is meaningful: one test seeds a spy `load` and asserts it fires on mount (`waitFor(() => expect(load).toHaveBeenCalled())`), and the tightened single-subscription test asserts `load` is called exactly once at mount and exactly twice after a `providersChanged` event, while `listen` stays at one call and `unlisten` is not called across navigation. Both fail if the startup `load()` line is removed. The `beforeEach` captures and restores the real `load`, preventing a spy leaking between the singleton-store tests — a real hazard now that the startup call runs on every `<App/>` mount.

### ProvidersChanged emit after successful mutations (bug B)

```
#[tauri::command] wrapper           emit_providers_changed(&AppState)
  let view = _inner(...).await?; ───────► core_events.send(CoreEvent::ProvidersChanged)  (let _ = ...)
  emit_providers_changed(&state);        │  fire-and-forget; dropped send never fails the mutation
  Ok(view)                               ▼
                                    providers.ts applyCoreEvent → refetch list_available_models
```

Each wrapper binds the `_inner` result with `?` so a validation or persist error short-circuits before the emit, then emits, then returns; a UI event that can't be delivered never fails the underlying mutation. All eight sites are wired, including the four embedded-model lifecycle commands that change what enumerates under Local.

The test gap is worth stating precisely. `rejected_mutation_does_not_emit_providers_changed` drives `set_cloud_provider_inner` with `ProviderKind::Ollama`, asserts `InvalidArgument`, and asserts `rx.try_recv().is_err()` — this genuinely exercises the "no emit on error" half of the contract, because `_inner` itself returns the error. But the eight positive tests drive `_inner` and then call `emit_providers_changed(&state)` in the test body, so they verify the helper enqueues the event, not that any wrapper calls it. If someone deleted the `emit_providers_changed(&state);` line from, say, `clear_local_runtime`, every test here would still pass. The task notes this is a deliberate consequence of not being able to construct a live `tauri::State` offline; the residual risk is that bug B's fix is not pinned by a regression test.

### Dead-code allow removal and secret hygiene

The variant is fieldless, so the `no_core_event_variant_carries_secret_material` exhaustiveness test keeps compiling with `ProvidersChanged` in both the events array and the match after the allow is dropped. On the frontend, `ProviderEnumerationErrors` renders only `error.providerId` and `error.message` (the `ProviderError` Display string), which is display-safe per the architecture's secret-hygiene sections; no resolved secret or `SecretRef` crosses into any new UI.

### Refresh affordance and visible errors

The "Refresh models" button lives in the `PerMessageOverrideControl` header with `type="button"`, `aria-label="Refresh models"`, and a `data-testid`, calling a `load` selector fire-and-forget. Two tests cover it: one clicks it and asserts `invoke("list_available_models")` fires and the fetched model becomes selectable (`findByRole`), the other asserts a spy `load` is called — both fail if the button or its wiring is reverted. This is the load-bearing diagnostic given the sandbox has no live provider endpoint: a "nothing happened" report now becomes either a visible error line or a populated picker after one click.

### Not tested

No test asserts the enumeration errors render as a consequence of the *startup* load path in the chat context (the existing model-selector error test seeds the store directly), so the end-to-end "startup load populates errors near the chat picker" flow is only verified on the user's live build. The eight wrapper emit sites are likewise not covered end-to-end (see above).
