# Orchestration core foundations — Phase 1 (P1.1–P1.7) (v1)

Phase 1 lays the framework-agnostic core for the hybrid orchestrator: the Section 7.1 domain models (with hand-mirrored TypeScript DTOs), a versioned SQLite persistence layer with per-entity repositories, an OS-keychain secret store that only ever exposes opaque `SecretRef` handles, a `SessionManager` with per-conversation write locks, the eleven-variant `CoreEvent` surface, and the Tauri command/event wiring that turns those into a validated IPC boundary. The offline sandbox can't reach crates.io, so the crates carrying registry deps (`orchestrator-core`, `persistence`, `secrets`, `tauri-app`) are moved under `[workspace] exclude` and built explicitly in CI — an accepted, documented split.

Watch for: a **circular crate dependency** between `orchestrator-core` and `persistence` (each lists the other as a normal `[dependencies]` path dep). This is a hard `cargo` error (`cyclic package dependency`) that the offline `--workspace` build cannot see because both crates are excluded — the per-crate CI builds that do compile them will fail to resolve. **[confirmed]** This is blocking and it also violates the Section 3.3 strictly-downward direction. Secondary: production `Db::open` uses a default multi-connection pool with no `busy_timeout`/WAL, so concurrent cross-conversation writes can hit `SQLITE_BUSY` **[likely]**.

**Verdict**: NEEDS_CHANGES

## High-level view

The dependency-direction defect is the headline. `orchestrator-core -> persistence` is correct per Section 3.3, but `persistence` was given a reverse edge back onto `orchestrator-core` so its repositories can name the domain model types. Two library crates with a normal-dependency cycle do not build; cargo rejects the graph before any compilation. The offline default build hides it because both ends are excluded from the workspace, so only the networked per-crate CI steps would surface it — as a resolve failure, not a clean signal. The fix is to break the cycle by moving the shared DTOs so persistence depends downward only (models in a leaf crate both depend on, or persistence defining its own row types).

The secret posture matches Sections 9.1/9.2: `SecretRef` serializes as a bare handle, has no plaintext accessor, `resolve` is the single core-internal seam and is never registered as a command, and `set_provider_secret` returns only the handle. One test gap — the "returns only a ref" assertion bypasses the command handler (see below).

The command surface validates every argument (UUID parse, non-empty, length bounds, tag/list counts) before touching the core and maps failures to a structured `CommandError`; the IPC allowlist is the `generate_handler!` registration, documented against Tauri v2's capability model.

Concurrency uses a per-conversation `tokio::Mutex` keyed by UUID, serializing writes within a conversation while letting different conversations proceed in parallel. Two gaps: the lock map only sheds entries on `delete_conversation`, so it grows with the number of distinct conversations touched, and the "writes serialized through the pool" claim doesn't hold for the production multi-connection pool.

The TS mirror tracks the serde representation, including the `PrivacyTag::Custom` externally-tagged `{ custom: string }` shape and the `type`-tagged unions.

1. **Circular crate dependency (blocking)** — `orchestrator-core` and `persistence` depend on each other as normal path deps; cargo rejects this with `cyclic package dependency` and it breaks the CI per-crate builds. Break the cycle so the direction stays downward (Section 3.3): relocate the shared domain DTOs to a leaf crate both depend on, or have persistence define its own row/DTO types.
2. **Cycle is invisible to the offline build** — because both crates are `[workspace] exclude`d, `cargo build --workspace` never resolves the cycle; only the networked CI steps hit it. After breaking the cycle, keep a check (even a `cargo metadata` resolve) that would catch a reintroduced reverse edge.
3. **SQLite busy under cross-conversation writes** — production `Db::open` uses the default pool (up to 10 connections) with no `busy_timeout` and default journal mode, while the per-conversation lock only serializes same-conversation writes. Concurrent writes to different conversations can return `SQLITE_BUSY`. Set WAL + a `busy_timeout` (or cap the pool to 1 writer). Tests never exercise this because they use the single-connection in-memory pool.
4. **Unbounded lock-map growth** — `SessionManager::lock_for` inserts a lock per conversation id and only `delete_conversation` removes one; a long-lived process that reads/writes many conversations accumulates entries. Consider evicting idle locks or keying differently.
5. **`set_provider_secret` command not covered end-to-end** — the "returns only a ref" test calls `secret_store.store` directly rather than the command handler, so the handler's validation + return path isn't exercised. Drive the command (or its inner body) so a future change to the handler that leaked the secret would fail a test.

### Circular dependency: `orchestrator-core` ↔ `persistence`

`orchestrator-core/Cargo.toml` lists `persistence = { path = "../persistence" }` (correct — Section 3.3 says the core depends on persistence). But `persistence/Cargo.toml` now lists `orchestrator-core = { path = "../orchestrator-core" }`, because `repositories.rs` imports the domain model types (`use orchestrator_core::{Conversation, Message, ...}`) to (de)serialize rows.

```
orchestrator-core ──deps──▶ persistence
        ▲                        │
        └──────── deps ──────────┘   ← reverse edge added in FEAT-002
```

A normal-dependency cycle between two library crates is a hard cargo error; the resolver refuses the graph before compiling anything:

```
error: cyclic package dependency: package `a` depends on itself. Cycle:
package `a` ... which satisfies path dependency `a` of package `b`
    ... which satisfies path dependency `b` of package `a`
```

(Reproduced locally with a minimal two-crate cycle.) So `cargo build --manifest-path crates/orchestrator-core/Cargo.toml` and the `persistence` equivalent — the exact commands the Phase 1 CI adds — cannot resolve. The offline `--workspace` build stays green only because both crates sit under `[workspace] exclude` and are invisible to it, which is precisely why this wasn't caught during local iteration.

The direction in Section 3.3 is unambiguous: `persistence`'s public types are `Db`, the repos, and `AppConfig`; it sits *below* the core. The repositories legitimately need the DTO definitions, so the DTOs are the thing in the wrong place. Options that restore a downward-only graph: move `models.rs` into a leaf crate (say `core-model`/`domain`) that both `orchestrator-core` and `persistence` depend on; or give `persistence` its own row structs and convert at the core boundary. The `SecretRef` re-export chain (`orchestrator-core` re-exporting `secrets::SecretRef`) does not drive the cycle and can stay; only the model types do.

### Secret hygiene and the `resolve` seam

`SecretRef(pub String)` serializes as a bare JSON string (asserted: `"provider-1"`) and exposes only `handle()`. The `SecretStore` trait keeps `resolve` — the one method returning plaintext — off the command surface: `set_provider_secret` is the only secret-touching command and returns `Result<SecretRef, CommandError>`, taking plaintext inward only. `ProviderRepo` binds `api_key_ref.handle()` into the column, and the round-trip test reads the raw column back to confirm it is just the handle string.

The `set_provider_secret_returns_only_ref` test asserts the right property but does so by calling `state.secret_store.store(...)` directly, not the command. The handler's own validation-then-store-then-return path is therefore untested; a regression that made the handler echo the secret wouldn't be caught. Exercising the handler body (or a thin extracted function) would close that gap.

### Argument validation and the IPC allowlist

Every handler validates before delegating: `parse_uuid` rejects malformed ids, `validate_nonempty`/`validate_opt_len` enforce trimmed-non-empty and character-count bounds, `validate_privacy_tags` bounds the count and rejects empty custom tags, and `PersonaInput::into_persona` parses each tool-server id and bounds the list. Failures map to `CommandError { code, message }` with an `ErrorCode` the frontend can branch on, and the error carries no secret material. The `From<SessionError>` mapping turns `ConversationNotFound` into a `NotFound` code and everything else into `Internal`. The allowlist is the `generate_handler!` list in `lib.rs`; `capabilities/default.json` documents that user commands are gated by registration (not capability tokens) in Tauri v2 and that no fs/shell/network capability is granted to the webview — consistent with Section 9.2 least privilege.

### Per-conversation write lock

`SessionManager` keeps `Arc<StdMutex<HashMap<Uuid, Arc<AsyncMutex<()>>>>>`: the outer std mutex is held only to fetch/insert a per-conversation `tokio::Mutex`, held across the async read-modify-write. Same-conversation writes serialize; different conversations get distinct locks and run in parallel. The concurrency tests cover both — eight concurrent appends to one conversation all persist, and interleaved writes to two conversations complete without deadlock.

Two caveats. First, `lock_for` inserts a lock entry per conversation id and only `delete_conversation` removes one, so a long-running process that touches many conversations grows the map without bound. Second, the module doc says "persistence writes are serialized through the SQLite pool" — that isn't true for the production pool. `Db::open` uses default `SqlitePoolOptions` (up to ~10 connections) with no `busy_timeout` and the default rollback journal, so two writers on different conversations (hence different pool connections) can collide with `SQLITE_BUSY`; the per-conversation lock doesn't help across conversations. The in-memory test pool pins `max_connections(1)`, so the tests never take the multi-connection path where this surfaces. Enabling WAL and a `busy_timeout` on `open` (or capping the writer pool) would make the doc claim hold.

### Persistence round-trips and migrations

Migrations are embedded via `sqlx::migrate!("./migrations")` and run on open; re-open is idempotent through sqlx's migration table, which the restart-survival test relies on. `0001_initial.sql` stores structured fields as JSON TEXT and enables `ON DELETE CASCADE` from messages to conversations, with `foreign_keys(true)` set on both `open` and `open_in_memory` so the cascade is enforced. Each repo has a real CRUD round-trip test (insert → get → mutate → list → delete) asserting on deserialized values rather than static shapes, and `update` returns `NotFound` on zero rows affected. `AppConfig` keeps `schema_version` in a dedicated authoritative column and a `#[serde(flatten)]` catch-all preserves unknown newer fields — the forward-compat test inserts `schemaVersion:2` + `futureFlag` and asserts both survive a load, exercising the real path rather than a shape assertion.

The restart-survival acceptance is a true round-trip: it writes a conversation and a persona to a temp SQLite *file*, drops the `SessionManager`/pool to simulate exit, reopens a fresh `Db` against the same path, and asserts both rows are present. Using `InMemorySecretStore` here keeps it keychain-free on headless CI.

### CoreEvent surface and the Tauri bridge

`CoreEvent` is a `#[serde(tag = "type", rename_all = "camelCase")]` union of eleven variants; the tests assert both a data variant (`messageDelta` with camelCase fields) and a unit variant (`providersChanged` → `{"type":"providersChanged"}`). Payloads carry only ids, deltas, statuses, and rationales — no secret or `SecretRef`. The `#[allow(dead_code)]` is documented to be removed once the Phase 2 pipeline constructs the remaining variants. The bridge (`spawn_core_event_bridge`) drains an unbounded channel and forwards over `CORE_EVENT_CHANNEL`, logging rather than propagating a failed emit so a dropped UI event can't tear down the core; `AppState` holds the sender for the Phase 2 pipeline.

### TypeScript mirror

`frontend/src/types/index.ts` tracks the serde representation: `Uuid`/`DateTime` → `string`, `Option<T>` → `T | null`, unit enums → camelCase string-literal unions (`ProviderKind` includes `openAI`/`lmStudio`/`genericOpenAI`), and internally-tagged enums → `type`-discriminated unions (`MessageContent`, `McpTransport`, `CoreEvent`). The tricky case is right: `PrivacyTag` has no `tag=` attribute, so its `Custom(String)` tuple variant serializes externally-tagged as `{ "custom": ... }` while unit variants are bare strings — mirrored as `'localOnly' | 'confidential' | { custom: string }`. `McpTransport`'s `Vec<(String,String)>` fields map to `Array<[string, string]>`, matching serde's tuple-as-array encoding. The command wrappers match the handler signatures (`create_conversation` wraps its struct as `{ args }`; scalar-arg commands pass named fields), and the vitest suite checks the invoke names and argument shapes.

### Workspace exclude/CI arrangement

The exclude-plus-explicit-CI pattern is documented in the root `Cargo.toml`, each excluded crate's manifest, and `ci.yml`, including the fmt-check-per-manifest steps and the `#[ignore]`d keyring test rationale for headless CI. One documentation claim is now wrong: that building `orchestrator-core`/`persistence` standalone "pulls those in through their `path` dependencies — the dependency edges are validated in CI". With the cycle present, that build fails to resolve rather than validating anything. Breaking the cycle makes the documentation accurate again.
