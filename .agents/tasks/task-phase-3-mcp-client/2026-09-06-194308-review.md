## High-level view

The dead-dependency removal is clean: `futures`, `futures-util`, and `bytes` are dropped from the manifest, no `use` referenced them (the SSE decoder was always a plain `str::split`), and every comment that previously claimed those crates backed "the SSE decoder" — two blocks in `Cargo.toml`, the `lib.rs` crate doc, and two spots in `ci.yml` — now states the decoder needs no futures/bytes machinery.

Both transports switched to a bounded `mpsc::channel(NOTIFICATION_BUFFER)` (256, a new documented `pub const` in `transport/mod.rs`) sending via `try_send`, so a chatty server can no longer grow client memory without bound. The stdio reader distinguishes `Full` (drop and continue) from `Closed` (stop the reader), preserving the original teardown. No orchestrator-core dependency was pulled in.

The reconnect backoff can no longer panic: the shift is capped at 31 and the `Duration` multiply uses `checked_mul` saturating to `Duration::MAX`, so any `max_reconnect_attempts` set through the public `HandleLimits` is safe. Growth stays exponential up to the cap, then plateaus.

The permission gate now matches on `effective` and passes `effective` into `prompt()`, so an emitted `PermissionRequested.mode` reflects the mode actually applied to the tool. A no-op today (overrides are always empty) but correct once per-tool overrides are wired.

The HTTP/SSE full-body buffering is retained and documented rather than rewritten — a module-level "KNOWN LIMITATION" plus a call-site comment covering the request-scoped-vs-server-push distinction, the deferral rationale, and the migration path. Given HTTP/SSE is CI-mocked and nothing in the current lifecycle consumes server-push, documenting the limitation is an acceptable Phase 3 disposition.

### Bounded notification channel

The stdio reader's match is the load-bearing detail:

```rust
match notif_tx.try_send(note) {
    Ok(()) => {}
    Err(mpsc::error::TrySendError::Full(_)) => {}
    Err(mpsc::error::TrySendError::Closed(_)) => break,
}
```

Dropping on `Full` keeps the reader from blocking, which would otherwise stall correlated responses; breaking on `Closed` preserves the prior "receiver gone, stop the reader" teardown. The HTTP/SSE side has no long-lived reader task, so its two `try_send` sites drop on full/closed without a break, which is consistent. `next_notification` drains with `recv().await` on the bounded `tokio::sync::mpsc` receiver. The drop-newest-on-full policy is documented on `NOTIFICATION_BUFFER`; correlated request/response traffic is unaffected because it rides a separate per-request `oneshot`.

### Reconnect backoff

`shift = (attempt - 1).min(31)` bounds the shift so `1u32 << shift` stays inside `u32`, and `reconnect_base_delay.checked_mul(multiplier).unwrap_or(Duration::MAX)` saturates instead of panicking on a `Duration` overflow. `attempt - 1` is guarded by the `attempt > 0` branch so it never underflows. Backoff doubles each attempt until the shift cap, then holds at the saturated ceiling — a safe upper bound regardless of how large a caller sets `max_reconnect_attempts` via the public `HandleLimits`.

### Effective mode in the permission prompt

`check()` matches on `effective = overrides.get(tool_name).copied().unwrap_or(mode)`, and the `Ask` arm now calls `prompt(server_id, tool_name, effective, rationale)`. The emitted `PermissionRequested.mode` reflects the mode applied after any per-tool override, resolving the v1 display inconsistency. Because `McpServerConfig` still has no overrides field, `effective == mode` in practice, so it is behavior-preserving today and correct once overrides are populated.

### HTTP/SSE buffering: documented, not rewritten

`post()` still awaits `resp.text()`, buffering the full body before `decode_sse_data_frames` splits it, so SSE remains request-scoped rather than a persistent server-push stream. The module doc and call-site comment now spell out the deferral rationale (a streamed decoder holding a `reqwest::Response` byte stream open is a larger rewrite that can't be exercised offline and carries regression risk) and the migration path (swap buffering for a streamed reader feeding chunks through the same frame splitter). The transport is CI-verified against a mocked server and no current lifecycle code consumes server-push notifications, so this stays a documented deferral rather than a blocking gap.

### Regression and clippy-risk sanity check

`grep` over `crates/mcp-client/src/**` finds no reference to `futures`, `futures-util`, `bytes`, `Stream`, or `StreamExt`, so the three deleted manifest lines were genuinely dead and their removal leaves no dangling `use`. The changes are localized to the five fix sites and introduce no obvious clippy `-D warnings` triggers: no new `if` nesting for `collapsible_if`, no `format!`/`{:?}` additions, and `MAX_BACKOFF_SHIFT`/`NOTIFICATION_BUFFER` are both referenced. `cargo fmt --check` passes for mcp-client, orchestrator-core, and tauri-app. Full build/clippy/test of the excluded crates remains CI-deferred (crates.io unreachable offline), which is expected. The remaining diff (task.json/FEAT-002.json) is metadata.
