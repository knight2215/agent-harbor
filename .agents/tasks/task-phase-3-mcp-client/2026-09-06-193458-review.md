# Built-in MCP client: transports, lifecycle, function-calling bridge, and permission model (v1)

Phase 3 fills the placeholder `mcp-client` crate with a real MCP client — stdio and HTTP/SSE transports over an in-crate JSON-RPC 2.0 layer, a per-server `McpServerHandle` lifecycle (initialize handshake, `tools/list` caching, on-demand invoke, bounded reconnect, teardown), and tool namespacing by server UUID — then wires it into `orchestrator-core` through a `ToolBridge` that attaches visible tools to a `ChatRequest`, resolves a namespaced tool call back to its owning server, validates arguments, runs an Ask/Allow/Deny permission gate, invokes, and normalizes the result into a `tool` message. All failure modes become structured `isError:true` tool messages rather than turn-crashing errors. `mcp-client` moves from workspace members to `exclude` and gains CI build/test/clippy/fmt steps on ubuntu + windows, ordered before `orchestrator-core`. A cross-platform stdlib mock MCP server backs the stdio tests in each of the two crates.

Watch for: (1) `mcp-client` declares `futures`, `futures-util`, and `bytes` dependencies that are never used in `src/` — dead dependency weight, not a clippy `-D warnings` failure (confirmed). (2) Server→client notifications are forwarded onto an unbounded channel that nothing ever drains, so a chatty long-lived server grows memory without bound (confirmed). (3) The reconnect backoff `reconnect_base_delay * 2u32.pow(attempt - 1)` can panic on overflow if a caller sets `max_reconnect_attempts` high; defaults are safe (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The transport layer is a single `Transport` trait (`request`/`notify`/`next_notification`/`shutdown`) with an `untagged` `JsonRpcMessage` that classifies frames by the presence of `id`, and two implementations. stdio spawns via `tokio::process` with no shell, correlates responses through a pending-`oneshot` map on a background reader task, and fails all pending requests on EOF so callers never hang. HTTP/SSE reuses the Phase 2 `providers` pattern (own `ensure_crypto_provider` ring-install, rustls-tls reqwest, a buffered SSE `data:` decoder).

The lifecycle handle matches Section 5.3/5.6: `visible_tools()` hides disconnected servers, `invoke()` applies a per-tool timeout and output-size cap returning a structured `ToolResult{is_error}` for every tool-level failure, and namespacing uses the server UUID so reverse-resolution is unambiguous even when a display name contains `__`. The one lifecycle gap is that server notifications are collected but never consumed.

The bridge and permission model match Sections 5.4/5.5/9.4. `handle_tool_call` never returns `Err`; unknown server, bad JSON, schema-validation failure, permission deny, invocation error, and timeout all become `isError:true` tool messages, with lifecycle errors additionally surfaced as `CoreEvent::McpError`. The `PermissionGate` fails closed to deny when no UI is listening or the request is cancelled. The registry is framework-agnostic (oneshot keyed by `request_id`); tauri-app holds it on `AppState` and `resolve_permission` forwards to it. Per-tool overrides are plumbed through the gate signature but always empty because `McpServerConfig` has no overrides field yet — a documented deferral.

The only new IPC type is `PermissionDecision { allow, remember }`, mirrored into `frontend/src/types/index.ts` in camelCase; `CoreEvent::PermissionRequested` is unchanged. CI wiring mirrors the providers block and is correctly ordered before orchestrator-core.

<summary>Issues (5)</summary>

1. **Unused mcp-client dependencies** — `futures`, `futures-util`, and `bytes` are declared in `crates/mcp-client/Cargo.toml` but referenced nowhere in `src/`; drop them (the SSE decoder is a plain string split, unlike `providers` which does use them). Not a `-D warnings` failure, but dead weight and a misleading dep list.
2. **Notifications never drained** — both transports forward server→client notifications onto an unbounded channel, but no session-layer code ever calls `next_notification()`, so a chatty long-lived server accumulates notifications without bound. Either drain-and-drop, drain into `CoreEvent`s, or use a bounded/dropping channel.
3. **Reconnect backoff can overflow-panic** — `reconnect_base_delay * 2u32.pow(attempt - 1)` in `reconnect()` will panic (pow overflow in debug, `Duration` mul overflow) if a caller sets `max_reconnect_attempts` past ~32 via the public `HandleLimits`. Cap the shift/exponent or use `saturating`/`checked` arithmetic.
4. **Ask-mode event advertises the server default mode, not the effective mode** — when a per-tool override resolves to `Ask` while the server default differs, `PermissionGate::prompt` emits the original `mode`, not `effective`; display-only today (overrides are always empty) but will mislead once overrides are wired. Pass `effective` through.
5. **HTTP/SSE fully buffers responses** — `post()` calls `resp.text()`, buffering the entire body before decoding SSE frames, so server→client SSE streaming is effectively request-scoped rather than long-lived. Acceptable for request/response MCP but does not deliver true server-push streaming per Section 5.2; note the limitation or switch to a streamed decoder.

<summary>Details</summary>

### Transport abstraction and JSON-RPC framing

The stdio reader is careful in the ways that matter for robustness: unparseable lines (stray server logging on stdout) are skipped rather than tearing down the transport, EOF drains and fails every pending request with `Closed` so no caller hangs, and a write failure removes the pending entry it just inserted so the map does not leak. Notifications are the exception — see below.

### stdio cross-platform spawn

`StdioTransport::spawn` uses `tokio::process::Command` with piped stdin/stdout, null stderr, no shell, and layers configured env on top of the inherited env; `CARGO_BIN_EXE_*` resolves the fixture path with `.exe` on Windows. The two fixture servers (`mcp-mock-server` in mcp-client, `tool-loop-mock-server` in orchestrator-core) are stdlib-only blocking loops; the duplication is justified in-comment because `CARGO_BIN_EXE_mcp-mock-server` is not set for a path-dependency's bins in the dependent crate.

### Undrained notification channel

Both transports own a notification path — stdio's reader task sends every `JsonRpcMessage::Notification` onto an `mpsc::unbounded_channel`, and `next_notification()` drains it — but no code in `session.rs` or the bridge ever calls `next_notification()`. The trait method exists only for the trait's completeness. For a request/response workload this is invisible, but for a long-lived server that emits progress or log notifications the unbounded channel grows for the life of the connection. The stdio reader stops once the receiver is dropped (`notif_tx.send(...).is_err()`), so teardown reclaims it, but a still-connected handle never does. A bounded channel with a drop policy, or an explicit drain, closes this.

### Handle lifecycle and resource limits

`invoke()` reads the transport under a short read-lock, releases it, then awaits `tokio::time::timeout` around the request, so a slow tool does not hold the lock. `cap_result` measures the serialized size and honors an `isError` flag inside the server payload. The exponent arithmetic in `reconnect()` is the one sharp edge:

```rust
let delay = self.limits.reconnect_base_delay * 2u32.pow(attempt - 1);
```

With the default of 5 attempts, `attempt-1` ranges 0..3 and this is safe. Because `HandleLimits` is public, a caller can set `max_reconnect_attempts` large enough that `2u32.pow(attempt-1)` overflows (panics in debug) or the `Duration` multiply overflows. Cap the exponent (e.g. `min(attempt-1, 20)`) or use checked/saturating math.

### Tool namespacing and reverse resolution

Namespacing by `config.id` (a UUID) rather than the display name is the right call: `resolve_namespaced` splits on the first `__`, and a UUID never contains `__`, so the round-trip is unambiguous even for a server named `my__server`. The collision test drives two servers with a bare `echo` and asserts distinct namespaced names that each reverse-resolve to the right server id — a real regression guard.

### Bridge: resolve, validate, permission, invoke, normalize

Argument validation is a deliberately shallow in-crate `validate_arguments` (object-ness, `required` presence, declared-property type agreement, open-world extras) rather than a heavy jsonschema dependency. `integer` accepts `i64`/`u64` while `number` accepts any numeric, so a float supplied for an `integer` field is rejected. Validation is skipped only when the tool is absent from the cache, in which case the invoke path reports the unknown-tool error structurally.

The permission gate fails closed: if the event channel is closed (`send` errors) the pending request is cancelled and the outcome is `Deny`; if the oneshot sender is dropped without a decision the outcome is `Deny`. A tool can never run without an explicit approval in Ask mode. One display-level inconsistency: `check` computes `effective = overrides.get(tool).unwrap_or(mode)` and, when `effective == Ask`, calls `prompt(..., mode, ...)` with the *server* mode rather than `effective`, so the emitted `PermissionRequested.mode` reflects the server default. Overrides are always empty today so this cannot currently be observed, but it should pass `effective` through before overrides are wired.

### Permission IPC surface and TS mirror

`Decision` is `rename_all = "camelCase"` with `#[serde(default)]` on `remember`, and the TS `PermissionDecision { allow: boolean; remember: boolean }` mirrors it; the default lets the frontend send `{allow}` alone. `resolve_permission` parses the `requestId` UUID before touching the registry (rejecting garbage as `InvalidArgument`) and returns `bool` for awaiting-vs-unknown. `CoreEvent::PermissionRequested` is unchanged, so no other TS drift.

### Test meaningfulness

The tests exercise real paths, not mocks-of-themselves. `tool_loop.rs` spawns the actual fixture over stdio and drives `attach_tools` → `handle_tool_call` end to end: it asserts the tool is attached, the call resolves to the fixture server, the result comes back as a `tool` message, and the scripted second turn completes — it would fail if resolution, permission, invoke, or normalization regressed. The `echo` fixture requires a string `text`, so the schema-validation-failure test (`{"text":123}`) flexes `validate_arguments` against a live descriptor. Ask-mode is driven on a spawned task that blocks on the event, then unblocks via `registry.resolve`. `stdio_roundtrip.rs` covers handshake/discovery/call, namespacing collisions, unknown-tool structured error, per-tool timeout (a 50ms limit against a 5s `slow` tool), and disconnected-hiding with cache retention. Not tested: the notification channel (consistent with it having no consumer) and the HTTP/SSE transport (CI-deferred, mocked, per the documented plan).

### CI wiring and workspace arrangement

`mcp-client` moves to `[workspace] exclude` (routing remains the sole offline member), and the header comment / exit-path note are updated to include it. CI adds a `cargo fmt (check, mcp-client)` step among the other fmt checks and `build`/`clippy --all-targets -- -D warnings`/`test` steps before the orchestrator-core steps, correct because orchestrator-core path-depends on mcp-client; macOS is not re-added. The unused `futures`/`futures-util`/`bytes` deps will not trip `-D warnings` (the `unused_crate_dependencies` lint is not enabled), but they contradict the header comment that lists them as used for "the SSE decoder" — the decoder is a plain `str::split`.
