# Phase 5 UI surfaces wired to Tauri commands/events (v1)

Phase 5 builds out the five React surfaces (chat, model selector, tool/MCP manager, agent editor, conversation history) on top of a shared IPC layer (`ipc/commands.ts`) and four Zustand stores, and adds 14 supporting `#[tauri::command]` handlers plus a runtime `McpRegistry` on `AppState`. The stores treat the core as authoritative (Section 7.3): actions delegate to commands, and a single top-level `onCoreEvent` subscription in the app shell fans every `CoreEvent` into each store's `applyCoreEvent` reducer. The IPC/serde contract between Rust and the hand-mirrored TS DTOs is tightly maintained, the per-message override seam matches Section 8.2, and the capability set stays at `core:default` least privilege.

Watch for: (1) **confirmed** — after `sendMessage`, the sent user message and the streaming assistant reply never appear in the chat surface until the conversation is re-opened, because nothing seeds the messages the delta/complete events key onto and no event triggers a message refetch. This is the one blocking issue. (2) **confirmed** — the pipeline persists the user message and the assistant reply but emits no `conversationUpdated`/`conversationCreated` on message append, so the history surface's `updatedAt`/ordering and any non-active conversation go stale until a manual reload. (3) **likely** — recorded scope no-ops (`stop_generation`, per-server-only `set_tool_permission`, preview-only `get_route_explanation`) are reasonable, but the stop button presents as functional while doing nothing.

**Verdict**: NEEDS_CHANGES

## High-level view

The event contract is the spine of this change and it is clean: `CoreEvent` is an internally-tagged camelCase union on the Rust side with per-variant `rename_all`, and the TS mirror in `types/index.ts` matches it variant-for-variant, as do the new command DTOs. The channel name (`core://event`) matches between `events.rs` and `events.ts`, and all 14 new commands are registered in `generate_handler!`.

The chat streaming path has a wiring gap. `send_message` spawns `run_turn`, which allocates the assistant message id internally and emits `messageDelta`/`messageComplete` against it. The frontend only learns that id from those events, but `applyCoreEvent`'s delta handler drops any event whose message id isn't already in `messages`, and nothing adds the new user or assistant message to the store on send. The result is that a turn produces no visible output until the conversation is re-opened. The store tests pass only because they pre-seed a message with the matching id.

The core→history sync has the same shape of gap at the conversation level: `SessionManager::append_message` emits nothing, so the history surface's per-conversation `updatedAt` and the message list of any non-active conversation drift from the persisted state between manual reloads.

The per-message override seam is implemented exactly as Section 8.2 specifies — a single transient value owned by the conversations store, written by `PerMessageOverrideControl`, consumed-and-cleared by the send path — and the `resolve_permission` wiring fix (0a00b77) correctly forwards the decision to the core before dequeuing.

Security posture holds for what it touches: no command returns secret material, event payloads are display-safe, and the loopback-locality check for the privacy hard constraint fails closed. The capability file stays at `core:default`.

The recorded scope decisions (`stop_generation` validated no-op, per-server-only permission, preview `get_route_explanation`) are defensible, but the stop control is presented to the user as a working button.

### Chat streaming never reaches the surface

This is the blocking issue. The send path in `state/conversations.ts` is:

```
sendMessage(content) -> consumePendingOverride() -> send_message(convId, content, override)
```

`send_message` (commands.rs) validates and spawns `run_turn` on a Tokio task and returns immediately; the assistant reply is meant to arrive via streaming events. Inside `run_turn` (pipeline.rs) the assistant message id is allocated up front (`let assistant_id = Uuid::new_v4()`), the user message is persisted, and `messageDelta { message_id: assistant_id, delta }` events fire per chunk, ending with `messageComplete { message_id: assistant_id, ... }`.

The frontend never learns `assistant_id` except through those events. But `applyCoreEvent`'s delta handler routes through `appendDelta`, which does:

```ts
const index = messages.findIndex((m) => m.id === messageId);
if (index === -1) {
  return messages; // dropped
}
```

Nothing adds a message with `assistant_id` to `state.messages` before the deltas arrive — `sendMessage` doesn't optimistically add the user's message or a streaming assistant placeholder, and `MessageList` only calls `openConversation` (refetch) when `activeConversationId` *changes*, not after a send. So every delta and the completion are silently dropped, and the user's own message never appears either. The turn only becomes visible if the user navigates away and back (re-triggering `openConversation`).

The pipeline side offers no seam to close this on the frontend alone: `SessionManager::append_message` emits no event, so there is no `conversationUpdated`/`messageStarted` to trigger a refetch, and the assistant id is generated too late to be known in advance. Closing this needs one of:

- return the assistant message id (or the seeded user+assistant messages) from `send_message` so the store can insert placeholders before deltas arrive; or
- emit a `messageStarted { conversationId, messageId, role }`-style event from `run_turn` before the first delta, and have the store append a placeholder on it; or
- have the store refetch `get_messages` on `messageComplete` (loses live streaming, but at least shows the result).

The first two preserve streaming; the third is a fallback.

### Message append emits no lifecycle event

Separate from the active-conversation streaming gap, `append_message` never emits `conversationUpdated` or `conversationCreated`. The conversations store refetches the index on those events (`applyCoreEvent` → `loadConversations` + `openConversation`), so the plumbing to react exists — but the events are never sent on a message append. Consequences: the history list's `updatedAt` (and any recency ordering built on it) doesn't move when a turn completes, and a conversation that isn't the active one won't reflect new messages until a manual reload. Emitting `conversationUpdated { conversationId }` after the user and assistant messages are persisted would drive both the history recency and (combined with the fix above) the message refresh.

### Stop control presents as functional

`stop_generation` is a deliberate validated no-op — it parses the id, confirms the conversation exists, and returns `Ok(())`, because the Phase 4 `run_turn` has no cancel token. The scope call is defensible; the UX is what to flag: the Composer renders an always-enabled Stop button wired to `stopGeneration`, so a user mid-stream can click it and nothing changes, with no signal that cancellation isn't wired. Disabling the button (or gating it behind a "generation in progress" state that also indicates it's unavailable) until the cancel seam lands avoids presenting a dead control as live.

### IPC/serde contract sync

Spot-checking the new types against their Rust definitions surfaces no drift:

- `RouteExplanation`: Rust marks `provider_id`/`model` with `skip_serializing_if = "Option::is_none"`; the TS mirror declares them optional (`providerId?`, `model?`) rather than `| null`, the correct match for skip-serialized fields.
- `McpServerInput` / `McpServerConfig`: `transport` uses the `McpTransport` internally-tagged union with `env`/`headers` as `[key, value]` tuple arrays — the TS `Array<[string, string]>` matches the Rust `Vec<(String, String)>` serde form.
- `CoreEvent`: 11 variants, per-variant `rename_all = "camelCase"` on the Rust side (the enum-level rename does not cascade to variant fields, so the per-variant attributes are load-bearing and present); the TS union matches field-for-field.
- Argument object keys in `commands.ts` are camelCase matching the Rust handler parameter names, and the `create_conversation`/`create_persona`/`add_mcp_server` wrappers nest under `{ args }` / `{ persona }` / `{ config }` to match the Rust signatures.

### Security and privacy posture

The locality signal for the privacy hard constraint is fail-closed: `local_provider_ids` treats only `LmStudio` and loopback-`GenericOpenAI` as local, and `is_loopback_endpoint` classifies anything it can't confidently parse as loopback as non-local — a parse ambiguity forces cloud-exclusion rather than leaking a `localOnly` conversation to a remote endpoint. The credential boundary is intact: `set_provider_secret` returns only a `SecretRef`, `list_available_models` resolves keys internally but returns only display-safe rows, and no event payload carries secret material. The `_inner` split on `set_provider_secret`/`list_available_models` keeps the no-secret-across-IPC invariant unit-testable.

### MCP registry lifecycle

`set_mcp_enabled(false)` calls `get` + `teardown` but leaves the handle in the map, whereas `remove_mcp_server` calls `remove` + `teardown`. The lingering handle stays in `send_message`'s snapshot. It's harmless today because `visible_tools` returns empty for any non-`Connected` handle, so a disabled server contributes no tools — but removing the handle on disable (mirroring `remove`) would keep the registry to the actually-live set and avoid a footgun if anything ever iterates the snapshot without checking state.

### Test coverage

The store tests exercise real reducer logic (delta accumulation, completion finalize, override consume-and-clear, permission enqueue/forward/dequeue, resume restoring the full record) rather than static assertions.

Not tested: the real send→stream flow. Every delta/complete/error store test pre-seeds `messages` with a message whose id equals the event's `messageId` (`streamingMessage("m-1", ...)`), so they validate the reducer given a matching message but never the production path where the id first arrives via the event with no message present. A test that calls `sendMessage` and then feeds a `messageDelta` for the freshly-created turn — with no pre-seeded message — would fail today and would have caught the streaming gap. Also untested: that a completed turn updates the history surface (no coverage of the `append_message`→lifecycle-event path, which currently doesn't exist).
