# Phase 5 review fixes: live streaming, history refresh, stop UX, MCP handle cleanup (v2)

The fix commit (`3cef351`) addresses all five v1 findings. A new `CoreEvent::MessageStarted { conversationId, messageId, role }` variant lets `run_turn` announce both the persisted user message and the streaming assistant reply before any delta, and the conversations store seeds a placeholder on it so deltas land on a real message instead of being dropped. `run_turn` also emits `ConversationUpdated` after each persist to refresh history recency, the Composer gates its Stop button behind an in-progress state, and `set_mcp_enabled(false)` now removes (not just tears down) the handle. New tests drive the real no-pre-seed send path and split the stop-button cases. The Rust/TS `CoreEvent` contract is back in exact sync (12 variants each, per-variant camelCase, `Role` matching), and `pipeline_e2e` still passes because it asserts events via `.any()`.

Watch for: the two active-conversation fixes now collide — emitting `ConversationUpdated` for the *active* conversation triggers a fire-and-forget `openConversation` refetch of `get_messages`, which replaces the whole `messages` array with persisted rows. The refetch kicked off after the user-message persist resolves during the assistant stream, when the assistant row is not yet persisted, and clobbers the freshly-seeded streaming placeholder and any accumulated deltas — disrupting the very live streaming issue #1 was meant to preserve (**likely**).

**Verdict**: NEEDS_CHANGES

## High-level view

The event contract is back in sync: Rust `CoreEvent` now has twelve variants including `MessageStarted`, each internally tagged and per-variant camelCase; the TS union in `types/index.ts` mirrors all twelve, and the new `role` field carries the domain `Role` enum whose camelCase serde (`user`/`assistant`) matches the TS `Role` string union. `pipeline_e2e` matches events with `.any()`, so the two new variants in the stream don't break it.

Issue #1's mechanism is sound in isolation: `run_turn` emits `MessageStarted` for the user message and again for the assistant reply before the first delta, and the store's new `messageStarted` handler appends a placeholder (user → `complete`, assistant → `streaming`), guarded against duplicate ids and non-active conversations, so deltas accumulate on a seeded message.

Issue #2 emits `ConversationUpdated { conversationId }` after both persists. For non-active conversations the store reacts with a `loadConversations` index refresh only. For the *active* conversation it additionally calls `openConversation`, and that is where the fixes interfere: the async `get_messages` refetch, resolving mid-stream, overwrites the store's in-flight streaming state.

Issue #3 is resolved: the Stop button is disabled unless some message is `streaming` and carries an explanatory title, so the validated-no-op `stop_generation` is no longer presented as a live control.

Issue #4 is resolved: `set_mcp_enabled(false)` removes and tears down the handle (mirroring `remove_mcp_server`) and emits `mcpStateChanged: disconnected`; re-enable re-inserts and connects, tearing down any prior handle first. A disabled server no longer lingers in `send_message`'s snapshot.

Issue #5 is resolved: a new store test drives `sendMessage → messageStarted(user) → messageStarted(assistant) → deltas → complete` with no pre-seeding and would fail if the placeholder-seeding regressed; a non-active `messageStarted`-ignored case and a `conversationUpdated` refresh-path case are added, along with the serde round-trip and split stop-button tests.

### `ConversationUpdated` on the active conversation clobbers the stream

Issue #1 and issue #2 both touch the active-conversation message list, and their fixes now race. The pipeline emits, in order on the same channel:

```
MessageStarted{user, complete}      -> store seeds user placeholder
ConversationUpdated                 -> active conv: void openConversation() -> get_messages() (in flight)
MessageStarted{assistant, streaming}-> store seeds assistant placeholder
MessageDelta * N                    -> accumulate on the assistant placeholder
MessageComplete                     -> finalize assistant
ConversationUpdated                 -> active conv: void openConversation() -> get_messages() (in flight)
```

The event handlers run in order, but `openConversation` is `async` and `void`-ed:

```ts
openConversation: async (conversationId) => {
  const messages = await getMessages(conversationId);
  set({ activeConversationId: conversationId, messages }); // replaces the whole array
},
```

The refetch fired by the first `ConversationUpdated` reads the DB at a point where only the user message is persisted — `get_messages` maps to `list_messages`, which returns persisted rows only, and the assistant row isn't written until `MessageComplete`'s persist. When that promise resolves (after the assistant placeholder and some deltas have already been seeded), its `set({ messages })` overwrites the array with `[userMessage]`, dropping the streaming placeholder and every delta accumulated so far.

The final state is likely to self-heal because the second `ConversationUpdated` (post-assistant-persist) triggers another refetch that returns the completed assistant row, so the reply reappears once streaming ends. But the live streaming in between is disrupted, which is exactly the behavior issue #1's fix set out to preserve: the assistant bubble can blank out mid-stream and only repopulate at completion. The `conversationUpdated` test mocks `get_messages` and asserts only that the refetch is *called*; it never interleaves a resolving refetch with in-flight deltas, so it doesn't exercise this race.

Two clean ways out: have the `conversationUpdated`/`conversationCreated` handler refresh the index (`loadConversations`) only and not refetch the active conversation's messages — the streaming events already keep the active list live — or guard the message refetch so it doesn't overwrite `messages` while a turn is streaming.

### Contract sync verification

`Role` is a domain enum with `#[serde(rename_all = "camelCase")]` over `System`/`User`/`Assistant`/`Tool`, serializing to `system`/`user`/`assistant`/`tool`, which matches the TS `Role = "system" | "user" | "assistant" | "tool"` — so the new `role` field on `messageStarted` crosses the bridge intact. The `message_started_round_trips_camel_case` test pins `"type":"messageStarted"`, the camelCase id fields, and `"role":"assistant"`, and asserts a round-trip back into the variant. Because `pipeline_e2e` matches events with `.any()` and never asserts an exhaustive event set or count, the two new variants it now sees are tolerated — no integration regression from the added emissions.
