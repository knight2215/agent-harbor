# Routing policy engine + end-to-end message pipeline (Phase 4) (v1)

Phase 4 adds the `routing` crate (a pluggable `RoutingPolicy` trait, complexity/privacy/cost signals, the `AutoDefaultPolicy`, a `ManualOverrideResolver` implementing the Section 6.3 precedence, and a selectable `PolicyRegistry`) and fills in the previously-stubbed `orchestrator-core` pipeline so `run_turn` assembles the full `message -> route -> provider -> bounded tool loop -> persist` turn, streaming `CoreEvent`s and persisting route + usage. It reuses the `domain`/`providers` DTOs rather than duplicating them, wires a `send_message` Tauri command + typed frontend wrapper, and moves `routing` from workspace `members` to `exclude` with matching per-crate CI steps. The privacy fail-closed path, capability filtering, and manual precedence are all implemented and unit-tested, and the e2e integration test genuinely drives the new pipeline through a real tool loop.

Watch for: a persona's `default_route` is silently ignored by the router — nothing in the routing crate or pipeline ever reads it (confirmed); the `CostBudget` signal is fully implemented and unit-tested but the pipeline hard-codes `budget: None`, so budget-aware routing is dead in production (confirmed); a per-message manual override to a provider/model missing from the freshly-enumerated `available` list is rejected as unavailable, which can turn a transient enumeration failure into a rejected manual pin (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The routing engine is layered cleanly: pure signal helpers (`signals.rs`) feed a two-phase automatic policy — a non-negotiable hard-constraint filter (capabilities, then local-only under a privacy tag) followed by a quality/cost ranking — and a `ManualOverrideResolver` wraps whichever automatic policy is active to enforce per-message > pin > automatic precedence. The privacy path fails closed correctly in both the automatic and manual routes: a `LocalOnly`/`Confidential` tag that can't be satisfied locally returns an error rather than falling back to cloud, and a manual choice that would leak local-only data to a non-local model is rejected.

Locality is inferred from `price == TokenPrice::ZERO` rather than an explicit marker. The heuristic is documented but its safe direction is asymmetric for the privacy filter: an unpriced cloud model reads as "local" and would be *allowed* under a local-only tag (a real misclassification risk), while a priced local model would be wrongly excluded.

The pipeline assembles the turn framework-agnostically, attaches MCP tools only when the chosen model is tools-capable and servers are connected, runs a bounded tool loop capped at 8 iterations, and centralizes failure handling so every error both emits `MessageError` and persists an `Error`-status message. Two persona-level wiring gaps stand out: `default_route` never reaches the router, and the cost budget is never populated.

Secret hygiene holds across the new surface (`CoreEvent`, `RoutingDecision`, `RouteMetadata`, and the command return types carry only display-safe ids/labels/prices), and the excluded-crate/CI arrangement matches the established pattern (concrete dep literals in `routing/Cargo.toml`, per-crate steps in dependency order, matrix untouched). rustfmt and prettier are clean offline on all touched files.

### Two-phase automatic policy and the fail-closed privacy filter

`AutoDefaultPolicy::filter_candidates` runs the hard constraints before any scoring: capability filtering first (a tools- or vision-requiring request drops every model that lacks the capability, erroring `CapabilityUnsatisfiable` if none survive), then, when `requires_local` holds for the privacy tags, it keeps only zero-priced candidates and returns `PrivacyConstraintUnsatisfiable` if that set is empty. There is no code path that falls back to a cloud model once a `LocalOnly`/`Confidential` tag applies, and the `local_only_fails_closed_when_no_local` test locks it in. Ranking runs only over the survivors and out-of-budget candidates are penalized by −1.0 rather than hard-filtered, so scoring can never resurrect a privacy- or capability-filtered model.

### Manual precedence and the manual privacy gate

`ManualOverrideResolver` implements Section 6.3: per-message `manual_override` wins (`source = Manual`), else `conversation_pref` (`ConversationPin`), else it delegates to the wrapped automatic policy (`Automatic`). Both manual paths run `resolve_manual`, which re-applies the hard constraints: under a local-only tag the route must resolve to a local (zero-priced) candidate or it's rejected `ManualRouteRejected`, and a required capability the manual target lacks is rejected `CapabilityUnsatisfiable` — a manual choice cannot leak local-only data to the cloud.

When the manual route names a provider/model that isn't in `available`, `resolve_manual` returns `ManualRouteUnavailable` (after the privacy check). Because the pipeline rebuilds `available` per turn via `list_models` (which "may hit the network per provider"), a transient enumeration failure or a provider slow to list can make a previously-valid manual pin fail hard. The spec says manual override "always wins"; the implementation trades some of that for validating capabilities against a concrete candidate row. The failure mode should be understood — a pinned model that momentarily drops out of enumeration becomes unroutable rather than being trusted.

### Locality by zero price

With no `is_local` marker on `AvailableModel`, both the automatic filter and the manual gate treat `price == TokenPrice::ZERO` as "local" (`is_local_price`). The safe direction is asymmetric for the privacy filter:

```
LocalOnly tag + candidate priced ZERO but actually cloud  -> ALLOWED (leak risk)
LocalOnly tag + candidate priced >0  but actually local   -> EXCLUDED (over-strict)
```

The first case defeats fail-closed for a specific misconfiguration: a user who leaves a cloud provider unpriced (or explicitly zero-prices it) makes it eligible under a `LocalOnly`/`Confidential` tag. The module doc frames a deliberate zero-price as "declared free/local," a reasonable read for cost — but privacy is a stronger guarantee than cost, and a mispriced cloud model silently satisfying a confidential tag is the exact leak the fail-closed rule exists to prevent. Worth either validating that zero-priced candidates are genuinely local at the config boundary, or surfacing the assumption where per-provider rates are entered.

### Persona wiring gaps: default_route and budget

The automatic policy reads `persona.routing_hint` to bias the quality/cost weights (including a small explicit nudge for `PreferLocal`). But `persona.default_route` is never read anywhere in the crate or the pipeline — grep confirms no reference outside the DTO definition. Section 6.1/8.4 describe `default_route` as a persona's "preferred provider/model" that feeds routing; as implemented it has no effect at all, so a persona set up with a default route routes as if it had none.

Separately, the pipeline constructs `RoutingRequest { ..., budget: None }` unconditionally. The entire cost-budget apparatus — `CostBudget`, `within_budget`, the −1.0 out-of-budget penalty, the budget mention in the rationale — is reachable only from unit tests, never in a real turn. Both are "wired the type through but not the value" gaps: documented routing inputs that are silently inert.

### Bounded tool loop and failure centralization

`run_turn` allocates the assistant message id up front (so streamed deltas and the final completion share it), then wraps `run_turn_inner` so that any `PipelineError` both emits `CoreEvent::MessageError` and persists an `Error`-status assistant message before returning — a persistence failure on that error path is intentionally swallowed so the original error surfaces. The loop is capped at `MAX_TOOL_LOOP_ITERATIONS` (8); a model that keeps requesting tools past the cap yields `ToolLoopExceeded` rather than looping forever.

The continuation signal is "the turn accumulated tool calls," not the finish reason — `stream_turn` drops the finish reason and keys off accumulated calls, treating a `ToolCalls` finish with no actual calls as final. When the model asks for tools but no bridge is attached (no connected servers, or a non-tools model), the accumulated text is taken as final instead of looping on an unsatisfiable request. Tools are attached only when `capabilities.tools` holds and at least one server is connected (Section 4.4 capability negotiation).

`stream_turn` filters streamed tool-call builders by non-empty name (`filter(|b| !b.name.is_empty())`): a tool call that never carries a name fragment is dropped silently rather than erroring. For the OpenAI-shaped streaming contract this holds, but it's a quiet assumption on the provider's fragment order/completeness.

### Integration test actually exercises the new paths

`pipeline_e2e.rs` drives `run_turn` end to end with an in-memory `SessionManager`, a scripted non-streaming mock `ChatProvider`, the real `PolicyRegistry`, and the bundled `tool-loop-mock-server` over stdio. `automatic_routing_runs_tool_loop_and_persists_route` scripts a tool-call response followed by a final-text response, so the assertion that the second turn's text delta was emitted only holds if the tool call was genuinely handled and fed back — the test would fail if the tool-loop assembly were reverted. It also asserts the persisted message is `Complete` with the routed provider/model, a non-empty rationale, `RouteSource::Automatic`, and the final turn's token usage. `manual_override_records_manual_source` confirms `Manual` flows through, and `ask_mode_blocks_then_unblocks_within_pipeline` confirms the permission gate blocks the tool call and unblocks on `PermissionRegistry::resolve` within the assembled pipeline.

Not tested: the failure side of the pipeline. No test drives a routing error (privacy-unsatisfiable / capability / manual-unavailable), a missing provider instance, or a tool-loop-exceeded turn through `run_turn` to assert `MessageError` is emitted and an `Error`-status message persisted. That error-and-persist path is the pipeline's own contribution (the routing errors themselves are unit-tested in the routing crate), so it is currently unguarded against regression.

### serde / TS-mirror consistency and secret hygiene

`RoutingDecision` and `CostBudget` derive serde with per-type `rename_all = "camelCase"` and `skip_serializing_if` on the optional budget fields, but neither crosses IPC (both are internal to routing/pipeline), so there is no new TS-mirror obligation for them; `RoutingRequest` correctly does not derive serde since it embeds live provider DTOs. The `send_message` command takes `override_route: Option<ManualRoute>` and the frontend forwards `{ conversationId, content, overrideRoute }`; Tauri's camelCase→snake_case arg mapping lines these up, and `ManualRoute`/`PrivacyTag`/`RouteMetadata`/`RouteSource`/`TokenUsage` already exist unchanged in the TS mirror (still `providerId`/`model`). The new surface adds no secret material to any event or return type, and the existing `available_model_is_display_safe` / `set_provider_secret_inner_returns_only_ref` tests still guard the boundary.

### Excluded-crate / CI arrangement

`routing/Cargo.toml` uses concrete literals (`version = "0.1.0"`, `edition = "2021"`, `async-trait`/`serde`/`serde_json`/`thiserror`, `tokio` dev-dep) with no `{ workspace = true }`, required now that it has no workspace root to inherit from. `hybrid-orchestrator/Cargo.toml` moves `routing` from `members` (now `[]`) to `exclude`. `ci.yml` adds fmt/build/clippy(`-D warnings`)/test steps for `routing` placed after `providers`/`domain` and before `orchestrator-core` in dependency order, with the matrix left at ubuntu+windows and tauri-bundle still gated. `orchestrator-core/Cargo.toml` promotes `futures-util` from dev-dep to a real dependency, matching the pipeline's new use of `StreamExt::next`. rustfmt (`--check`) passes for all three touched crates and prettier passes for the touched frontend files offline; crates.io-dependent build/clippy/test are left to CI under INTEGRATIONS_ONLY.
